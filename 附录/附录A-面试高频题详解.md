## 第 1 题：设计一个 RAG 系统，说明每一层的优化手段

**考察意图**：是否真做过全链路（还是只会调框架），以及工程深度。

**答题框架**（按数据流向逐层走）：
1. **文档解析**：格式（PDF/Word/MD/网页）→ 解析器选择；表格与图文的处理策略
2. **切片（Chunking）**：固定长度 vs 语义切片；chunk 大小与重叠的取舍（小=检索准但上下文碎，大=反之）；标题/元数据随片携带
3. **Embedding**：模型选型（多语言/中文支持、维度、成本）；批处理入库
4. **向量库**：选型理由（LanceDB/pgvector 入门——本课程主线是嵌入式的 LanceDB，已有 PostgreSQL 就用 pgvector；Qdrant 生产；Milvus 大规模）+ 索引类型（HNSW）与元数据过滤
5. **检索层**：单路向量 → **混合检索（向量 + BM25）+ RRF 融合**——为什么需要（专有名词、精确匹配场景向量会漏）
6. **重排（Rerank）**：召回 top50 → rerank 精排 top5；交叉编码器为什么比向量相似更准
7. **生成层**：注入位置（资料放中间、指令首尾）、引用溯源（回答标注来源编号）、「资料没有就说不知道」
8. **评测层**：评测集（20+ 条）+ 忠实度/召回率指标 + Bad Case 归因

**加分点**：讲一个真实调优故事（「召回率差 → 分析发现是切片过粗，语义切片后提升 X%」）；提到查询改写/HyDE/GraphRAG 等进阶手段及适用边界。

**避坑**：只说「用 LangChain 搭」不讲每层的为什么；没有评测意识（这题必追问「你怎么知道效果变好了」——见第 7 题）。

关联章节：第 12、13、15 章。

## 第 2 题：Function Calling 的完整流程；工具调用失败/超时怎么办

**考察意图**：Agent 基础机制的原理级理解 + 容错思维。

**答题框架**：
1. **流程**：定义工具 schema（名称/描述/参数 JSON Schema）→ 随请求发给模型 → 模型返回「我要调用 X 工具，参数是 Y」（此时不生成最终答案）→ **你的代码**执行该函数 → 结果作为 tool 消息回传 → 模型基于结果继续（生成答案或再调用）——强调「执行永远在你的代码里，模型只做决策」
2. **失败处理分层**：
   - 参数错误：schema 校验拦截（Zod）→ 把校验错误回传让模型自修正（重试 1-2 次）
   - 执行超时：超时上限 + 取消 + 向模型返回结构化错误信息让它决策（换工具/问用户/放弃）
   - 业务失败：错误也回传（模型能理解错误并调整），但区分「可重试错误」与「致命错误」
   - 兜底：单工具最大重试次数、总步数上限、连续失败熔断转人工
3. **正确性**：描述写清楚「什么时候用我/什么时候不用我/参数含义/错误码含义」——工具描述质量直接决定调用准确性

**加分点**：讲清并行工具调用的硬规则——模型一次可能返回多个 `tool_calls`，assistant 消息里的**每个** `tool_call.id` 都必须有一条对应的 `role: "tool"` 回执（执行失败、跳过也要回一条错误结果），否则下一轮请求直接 400（第 8 章，配套 `code/src/agent/loop.ts`）；参数越界的应用层校验（schema 合法 ≠ 有权限，不能只信模型给的参数）；OpenAI GPT-6 系的工具调用只走 Responses API（`function_call` / `function_call_output` 按 `call_id` 配对，规则同构）（2026-11 复核）。

**避坑**：把 tool calling 说成「模型去执行函数」——这是原理性错误，直接出局。

关联章节：第 7、8 章。

## 第 3 题：Agent 死循环/任务中断怎么处理？长任务的暂停/取消/断点恢复？

**考察意图**：生产级 Agent 经验；这是「Demo 与生产」的分水岭题。

**答题框架**：
1. **死循环检测**：连续 N 步无进展判定（相同工具+相同参数重复出现、状态哈希不变）；步数上限；token/成本预算熔断
2. **任务中断**：执行每步后持久化状态（checkpoint）；中断源（用户取消/超时/异常）统一成事件
3. **断点恢复**：状态快照存外部（DB/文件），重启后从最后 checkpoint 续跑，已完成步骤不重算（幂等设计：步骤设计成可重放）
4. **长任务管理**：暂停/取消 API；进度上报（用户可见的步骤状态）；Human-in-the-loop 审批点（审批期间任务挂起）
5. **可观测**：每步记录轨迹（调用/参数/结果/耗时/token），出问题能回放定位

**加分点**：提到用持久执行框架（如 Inngest/LangGraph Checkpointer）而不是手写状态机，并说清 checkpointer 必须持久化（内存版换进程恢复会得到空状态）；讲「意图日志 + 幂等键 + 重启核对」：写操作执行前先记 started，成功记 succeeded，同一幂等键再来直接返回旧结果，停在 started 的先去业务系统核对再决定是否重试（配套 `code/src/reliability/ledger.ts`）。

**避坑**：只答「加重试」——重试解决不了死循环；没有持久化概念的恢复是空谈。

关联章节：第 8、10、17、22 章。

## 第 4 题：Agent 的记忆与状态管理怎么设计？

**考察意图**：上下文工程理解深度（2026 年 JD 最高频新词，字节 Aime、DeepSeek、腾讯均写进 JD）。

**答题框架**：
1. **分层模型**：短期记忆（当前会话上下文/滑动窗口）、长期记忆（跨会话持久化的事实与偏好）、情景记忆（过往交互经历，可检索）、语义记忆（提炼的知识）——各自举一个例子
2. **写入路径**：什么时候沉淀记忆（会话结束/轮次间隙）、怎么抽取（LLM 抽取结构化事实）、怎么去重合并
3. **读取路径**：按相关性检索注入（本质是「对记忆做 RAG」），受上下文预算约束
4. **生命周期**：过期、冲突（新旧信息矛盾时以新为准并记录）、用户可查看可删除（隐私合规）
5. **工程实现**：存储（PG/向量库）、MemGPT 思想（上下文=虚拟内存，内外存分页）

**加分点**：讲「记忆整理（consolidation）」后台过程；坦诚讲自己项目里做到哪一层（做了一半的诚实比背概念强）。

**避坑**：把记忆等同于「把历史消息都存下来再全量塞回去」——那是没有记忆管理。

关联章节：第 14 章。

## 第 5 题：多 Agent 架构怎么设计？编排模式、任务分发、结果聚合、冲突处理？

**考察意图**：架构设计能力；「多 Agent」是不是只会堆概念。

**答题框架**：
1. **先答「什么时候才需要多 Agent」**：单 Agent 上下文/职责过载、需要并行、需要隔离权限时才拆；否则单 Agent + 多工具更稳（这个反向判断是最大加分点）
2. **编排模式**：主从式（Orchestrator-Workers，规划者分发、执行者干活、主控聚合）——最常用；流水线（按阶段串行）；辩论/评审式（生成者+批判者）；去中心化（少用，难控）
3. **任务分发**：任务描述结构化（目标/输入/输出格式/验收标准）；子 Agent 的上下文隔离（只给所需信息，防止污染）
4. **结果聚合**：结构化输出保证可聚合；冲突时主控仲裁（或规则仲裁：时间新者优先/人工裁决）
5. **工程问题**：成本（N 个 Agent = N 倍调用）、延迟（串行/并行的选择）、错误传播（子 Agent 失败的重试与降级）、全链路追踪（哪个 Agent 出的问题）

**加分点**：协议分层——MCP 连工具（2026-07-28 版规范改为无状态：每个请求自带协议版本、服务端实现 `server/discover`、服务器向客户端要输入改用 MRTR），A2A 连 Agent（v1.0，现由 Linux 基金会旗下 AAIF 托管），AG-UI 连用户界面（2026-11 复核）；「多 Agent 的收益是隔离与并行，代价是复杂度与成本」的量化表述。

关联章节：第 11 章。

## 第 6 题：确定性程序、工作流与 Agent 的适用边界（Anker 原题）

**考察意图**：产品与架构判断力——会不会「手里拿着锤子看什么都是钉子」。

**答题框架**：
1. **确定性程序**：规则明确、输入输出可枚举、正确性可断言（计算价格、状态机流转、CRUD）→ 永远用普通代码
2. **工作流（Workflow）**：流程固定、每步可能用 LLM，但**编排由代码写死**（先摘要→再分类→再路由）→ 用确定性编排 + LLM 节点；可预测、可测试、成本可控
3. **Agent**：流程无法预枚举、需要模型**自主决定**下一步（开放性任务、多轮工具探索）→ 循环 + 终止条件 + 预算；灵活但贵、慢、难测
4. **决策标准**：能预先画出流程图的用工作流；画不出来（依赖执行中信息决定分支）才用 Agent；能用 if-else 的别惊动模型
5. **混合现实**：生产系统大多是「工作流为骨、局部 Agent 为肉」（如：固定流程中的自由检索环节用 Agent）

**加分点**：引用 Anthropic《Building Effective Agents》的观点（「从最简单的方案开始，只在需要时增加复杂性」）；给自己的项目举一个「从 Agent 降级为工作流后稳定性/成本双升」的例子。

关联章节：第 8、10、11 章。

## 第 7 题：怎么证明你的 Agent/RAG 比 baseline 好？

**考察意图**：评测能力——「工程师与调参侠的分水岭」（Shopee、Anker、自变量机器人的核心考点）。

**答题框架**：
1. **先有评测集**：从真实使用/业务场景攒 20-100 条（问题+期望要点/标准答案），覆盖典型+边界+对抗样本
2. **定指标**：RAG：忠实度（回答是否基于资料）、上下文召回/精确率、答案相关性；Agent：任务完成率、步数/成本效率；都是「样本通过率」口径
3. **评测方法**：规则断言（关键词/格式）+ LLM-as-Judge（评分 prompt 也要校准——抽 20% 人工比对一致性）+ 人工抽检
4. **对比实验**：控制变量（同评测集、同参数、多 seed），baseline vs 改动版，报告均值与差值；线上再小流量 A/B
5. **失败归因**：错例分桶——模型能力问题/检索没召回/上下文组装问题/工具执行问题，各占多少；改进打在最痛的桶

**加分点**：把评测做成 CI（promptfoo 接 GitHub Actions，改 Prompt/模型自动回归）；提评测集本身的迭代（Bad Case 进集）；区分「离线回归」（FakeModel 按脚本回放，验证循环会停、越权被拒等程序逻辑，零成本）与「真实评测」（验证模型 + 提示词的效果）；知道生态变化——OpenAI 自家 Evals 平台已弃用（2026-10-31 只读、2026-11-30 关停），官方迁移指引指向 promptfoo（2026-11 复核）。

**避坑**：「感觉好了」「问了几个朋友都说不错」——直接暴露没做过生产。

关联章节：第 15、13 章。

## 第 8 题：成本与延迟怎么优化？

**考察意图**：unit economics 意识（影析、绿联、易京 JD 的明确要求）。

**答题框架**：
- **成本侧**：模型路由（简单任务小模型，难任务旗舰——按任务类型/置信度分流）；Prompt 缓存（稳定前缀放前面，命中打折；OpenAI 默认自动缓存，Claude 要显式加 `cache_control`）；上下文压缩（历史摘要、检索片段精选）；输出长度控制（max_tokens、要求简洁）；批处理（离线任务走 Batch API 打折）；结构化输出省去重试
- **延迟侧**：流式输出（首 token 时间才是用户感知的延迟）；并行工具调用与并行子任务；缓存高频问答（语义缓存）；控制上下文长度（输入越长首 token 越慢）
- **监控**：每次调用记录 token 用量与耗时，按功能/用户/模型聚合出成本看板；设置预算告警
- **算账**：现场算一次单任务成本（输入×单价 + 输出×单价），给出优化前后对比

**加分点**：成本-质量-延迟三角的取舍表述（「我们接受分类任务 2% 的准确率下降换 70% 成本下降」这种量化决策最加分）。

关联章节：第 17、16 章。

## 第 9 题：流式输出（SSE/WebSocket）的前后端实现（前端转岗者的天然送分题）

**考察意图**：确认你的前端存量 + 是否理解 LLM 流式的特殊性。

**答题框架**：
1. **为什么 LLM 天然是流式**：token 逐个生成（第 1 章原理），等全部生成完首屏可能要 10s+，流式把「总时长」变「首 token 时长」
2. **SSE 原理**：HTTP 长连接 + `text/event-stream` + 服务端逐事件推送 `data:` 帧；浏览器端 `EventSource` 或 fetch + ReadableStream（后者可 POST、可带 header——LLM API 都要 POST，所以实战用 fetch 流式读取）
3. **前端渲染**：增量追加 + 自动滚动；**性能要点**——高频 setState 的节流/合并（每 50-100ms flush 一次而非每 token）、长对话虚拟列表、Markdown 增量解析（未闭合代码块的处理）
4. **后端实现**（Node）：把上游模型的流转发给客户端；断线重连（Last-Event-ID）；异常时发 error 事件优雅收尾
5. **SSE vs WebSocket**：单向推送 SSE 足够且更简单（走纯 HTTP、自动重连、CDN 友好）；双向实时（语音、协作）才上 WS
6. **协议层**：Vercel AI SDK 的 UI Message Stream 协议（旧称 Data Stream Protocol；在 SSE 上带结构化部件：文本/工具调用/审批/自定义 data）；跨框架的标准是 AG-UI 1.0

**加分点**：讲「工具调用过程可视化」——流式不只文本，工具调用的开始/进行/结束也是事件流（第 20 章核心内容，前端独有优势题）。

关联章节：第 5、20 章。

## 第 10 题：你平时怎么用 Claude Code / Cursor？怎么确认 AI 没给你挖坑？

**考察意图**：AI 编程工具是 2026 第一硬技能（50+/103 岗位要求）；多家公司把「书面回答这题」作为筛选。

**答题框架**：
1. **工作流**：什么任务交给 AI（样板代码/测试/重构/陌生领域探索）什么不交（核心业务逻辑自己写）；「先 spec 后生成」的习惯（SDD）
2. **上下文工程**：项目级 Rules（CLAUDE.md：技术栈/目录约定/编码规范/禁项）；任务级（把相关文件、接口定义喂全——上下文不足是 AI 犯错主因）
3. **质量闭环**：类型与 Lint 挡第一道；单测（AI 写码 AI 测但用例我自己审）；Code Review 聚焦逻辑而非风格；「看不懂的代码不合并」
4. **验证方法**：边界输入跑一遍、对照 spec 逐条验收、在预发环境冒烟；高风险改动（支付/权限/删除）人肉逐行
5. **提效数据**：给出真实数字（如「样板与测试代码 60-70% 由 AI 生成，整体交付提速约 X%」——有你日志里的数据最好）
6. **方法论沉淀**：把团队共性问题做成 Rules/Skills/模板，而非每人自己踩坑

**避坑**：说「我全让 AI 写然后直接上线」——在考察质量意识的语境下等于自杀；说「我不太用 AI」——岗位直接要求深度使用。

关联章节：第 6 章（+ 你的 AI 使用日志）。

## 第 11 题：ReAct / Plan-and-Execute / Reflexion 的原理与出处

**考察意图**：易京等岗位明说「读过论文且能讲清楚」——Agent 原理门槛。

**答题框架**（每篇：出处 + 核心思想 + 局限 + 你的实践）：
1. **ReAct**（Yao et al., 2022, arXiv:2210.03629）：推理与行动交替——Thought→Action→Observation 循环；把「边想边做」交给模型；现代 Agent Loop 的直接源头。局限：逐步思考在长任务上易漂移。实践：第 8 章你手写过
2. **Plan-and-Solve / Plan-and-Execute**（Wang et al., 2023, arXiv:2305.04091）：先出完整计划再逐步执行（规划与执行分离）；优点是步骤少走弯路、可并行、计划可审查；缺点是计划僵化，需要重规划机制。实践：多 Agent 项目里的规划 Agent
3. **Reflexion**（Shinn et al., 2023, arXiv:2303.11366）：失败后自然语言自我反思，存入情景记忆，下轮改进——「口头强化学习」不改参数。实践：给 Agent 加「失败复盘→重试」环节
4. **组合视角**：生产系统通常是 Plan-and-Execute 骨架 + 每步内 ReAct + 失败时 Reflexion——三篇论文是一个工具箱的三件工具

**加分点**：讲清「为什么 2026 年这些模式内建进了框架」（LangGraph 的图/节点/边就是这些模式的工程化）；能报出 arXiv 编号（准备过和没准备过的区别）。

关联章节：第 8、11 章 + 必读论文清单（附录 B）。

## 第 12 题：Prompt 注入怎么防？工具权限和沙箱怎么设计？

**考察意图**：安全意识（企业级/海外岗硬要求；OWASP LLM01）。

**答题框架**：
1. **威胁模型**：直接注入（用户输入夹指令）/间接注入（网页/文档/邮件内容里藏指令）；「模型遵循指令是概率行为，system 不是安全边界」
2. **纵深防御**：
   - 输入层：用户内容隔离（标签包裹+声明数据属性）、可疑模式过滤
   - 模型层：指令与数据分离的提示设计、（可选）独立小模型做输入审查
   - 输出层：生成内容过校验（格式/白名单/敏感词）、防数据外传（输出里不得含内部 URL/Key 模式）
   - **权限层（最关键）**：最小权限——工具按任务授予、高危工具需人工确认、凭证作用域收窄、只读优先
   - 执行层：不可信代码进沙箱（E2B/容器隔离，无网络、限文件系统）、速率与预算限制
3. **流程层**：红队测试（promptfoo red-team）常规化；出事可审计（全链路日志）
4. **认知层**：注入无法 100% 根治（与 SQL 注入不同，指令与数据同载体）——目标是「被注入后损失可控」

**加分点**：OWASP LLM Top 10（2025 版）能点出几条（LLM01 注入/过度代理/供应链/敏感信息泄露）；知道 OWASP 另有专门针对 Agent 的 **Agentic Top 10（2026 版，2025-12-09 发布，ASI01-ASI10）**——一句话：「LLM Top 10 管模型应用，Agentic Top 10 管会调工具、带委托权限行动的 Agent」，并能把它和自己项目的权限矩阵、沙箱、熔断、审批对上号（2026-11 复核）；「权限层的价值大于提示层的价值」这个判断；权限检查默认拒绝、只依赖代码与会话上下文，不依赖模型说了什么（配套 `code/src/security/permissions.ts`）。

关联章节：第 18、7、9 章。

## 第 13 题：（产品思维题）给一个模糊业务需求，现场拆解为 AI 方案

**考察意图**：从「实现者」到「方案设计者」——AI Native 公司（Kapibala、小步网络等）的核心面法。

**答题框架**（现场拆解四步法）：
1. **澄清**：用户是谁、痛点、成功标准、不能接受什么（幻觉率/延迟/成本的红线）——先问再设计
2. **拆任务**：流程里哪些步骤是「确定性」的（普通代码）、哪些是「理解/生成类」的（模型）、哪些需要「自主决策」（Agent）；**先画非 AI 流程图，再标 AI 增益点**
3. **设计**：每步的输入输出契约（结构化）、模型选择（贵模型只干难活）、失败兜底（低置信度澄清/降级/人工）、人工审批点（钱/删除/外发）
4. **度量**：上线后怎么衡量（完成率/满意度/成本/延迟）；小流量验证路线（先 5% 用户）
5. **反问**：预算多少、数据在哪、合规要求——展示全局感

**加分点**：主动算成本账（「这个方案单次任务成本约 ¥0.2，日均 1 万次是每天 2 千元，所以我加了缓存」）；提出「先工作流后 Agent」的保守路线。

**避坑**：上来就说「用 Agent + RAG + 微调全家桶」——暴露没有成本与复杂度意识。

关联章节：第 22 章「动手练习」第 5 题（专门练这个）；第 6 题（工作流 vs Agent）是它的前置。

## 第 14 题：（前端向）生成式 UI / Agent 执行过程可视化怎么设计？

**考察意图**：前端×AI 交叉领域的标杆题（八爪鱼、华为云、腾讯 JD 原文要求）。

**答题框架**：
1. **Agent 执行的可视化状态机**：任务→规划中→执行中（多工具并行/串行）→等待审批→失败重试→完成；每步展示：工具名/输入摘要/状态/耗时/结果摘要——数据来源是流式事件流（不只是文本 token）
2. **生成式 UI（Generative UI）**：模型输出结构化「组件意图」（JSON：类型+props）→ 前端映射到受控组件白名单渲染（安全：组件白名单，不是让模型生成任意 HTML/代码）
3. **流式渲染性能**：token 级事件合并批量渲染、Markdown 增量解析、长列表虚拟化、思考过程可折叠
4. **交互设计**：可中断/可重试/可编辑中间结果（Human-in-the-loop 的 UI 面）；错误态的友好呈现（「检索失败，已重试」）
5. **工程**：前端消费统一的事件协议（Vercel AI SDK 的 UI Message Stream，或跨框架的 AG-UI），UI 状态 = 事件流的 fold（reduce）；审批卡直接用 AI SDK 原生工具审批（服务端 `toolApproval`，前端 `addToolApprovalResponse`），跨会话审批再落库

**加分点**：强调「生成式 UI 的安全边界在组件白名单+props 校验（Zod）」——把前端工程经验与 AI 安全意识连起来，这正是「前端是差异化优势」的证明。

关联章节：第 20 章。

## 使用建议

1. **时间线**：求职前 4 周开始，每周过 3-4 题；每题准备一个「项目实例锚点」（你的项目 1/2/3 中的真实细节）
2. **模拟**：用 AI 当面试官（把题目给它，让它追问三连：「为什么？怎么验证的？还有什么方案？」）——注意，这只是练习，真正的面试官会抓你的项目细节
3. **诚实策略**：没做过的部分直说「这部分我在项目里做到 X 层度，再往下的方案我了解但没实践」——比编造安全得多，追问两轮必露馅
