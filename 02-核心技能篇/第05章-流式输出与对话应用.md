## 5.2 先手写 SSE：协议原理一次搞懂

### 服务端：SSE 长什么样

SSE = HTTP 响应以 `text/event-stream` 打开**不关闭**，服务端持续写入事件块：

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: {"delta":"你"}

data: {"delta":"好"}

data: [DONE]
```

规则很简单：每个事件以 `data: ` 开头、空行结尾；`event:`/`id:`/`retry:` 是可选字段（`id` + `Last-Event-ID` 请求头实现断点续传）。**它是单向的**（只能服务端推），但这正好匹配 LLM 场景（用户请求一次，模型持续吐 token）。

在第 2 章的 `hello-llm` 项目里，用 `lib/ai.ts` 的 `getClient()` 手写一个裸 SSE 接口（Hono，轻到不用解释）。先装两个包：

```powershell
pnpm add hono @hono/node-server
```

```ts
// server.ts —— 手写流式接口：理解原理版（pnpm add hono @hono/node-server）
import { Hono } from "hono";
import { serve } from "@hono/node-server";
import type OpenAI from "openai";
import { getClient, MODEL } from "./lib/ai";

const app = new Hono();

app.post("/api/chat", async (c) => {
  const { messages } = await c.req.json<{ messages: OpenAI.Chat.ChatCompletionMessageParam[] }>();
  const signal = c.req.raw.signal;   // 浏览器断开 / 用户点停止时，这个 signal 会被中止

  // 演示手写流循环（生产用 AI SDK，见 5.3）；signal 传给上游：客户端走了，模型请求也立刻停
  const upstream = await getClient().chat.completions.create(
    { model: MODEL, messages, stream: true, max_tokens: 1024 },
    { signal },
  );

  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async start(controller) {
      try {
        for await (const chunk of upstream) {
          const delta = chunk.choices[0]?.delta?.content ?? "";
          if (delta) controller.enqueue(encoder.encode(`data: ${JSON.stringify({ delta })}\n\n`));
        }
        controller.enqueue(encoder.encode("data: [DONE]\n\n"));
        controller.close();
      } catch (err) {
        if (signal.aborted) console.log("[sse] 客户端已断开，上游生成已中止");
        else controller.error(err);
      }
    },
    cancel() {
      upstream.controller.abort();   // 下游读者取消时，主动掐断上游
    },
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      Connection: "keep-alive",
    },
  });
});

// Node 下要显式监听端口（export default app 只在 Bun/Workers 这类运行时会自动启动）
serve({ fetch: app.fetch, port: 3000 }, (info) => console.log(`SSE 服务：http://localhost:${info.port}`));
```

运行：`pnpm exec tsx server.ts`。注意 `{ signal }` 那一行——**它决定了「停止」是不是真的停止**：浏览器断开连接时 `c.req.raw.signal` 被中止，SDK 随即断开与模型厂商的连接，模型不再继续生成，你也不再为后面的 token 付钱。我们用一个本地假模型端点验证过：客户端在第 8 个 token 时断开，上游在第 7 个 chunk 后就收到了断开（2026-11 复核，`@hono/node-server` 会把客户端断开传到 `signal` 上）。

### 客户端：为什么不用 EventSource

浏览器原生的 `EventSource` **只支持 GET、不能自定义 header**——而 LLM 接口要 POST 消息数组。所以实战全部用 `fetch` + `ReadableStream` 手动解析（下面这段就是你以后看任何流式库的底牌）：

```ts
// client.ts —— 手写流式客户端（在浏览器里运行：与 server.ts 同源的页面中调用）
type Msg = { role: "user" | "assistant"; content: string };

export async function streamChat(messages: Msg[], onDelta: (d: string) => void, signal?: AbortSignal) {
  const res = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ messages }),
    signal,                               // 「停止」按钮：controller.abort() → 连接断开 → 服务端也停
  });
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`);

  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";                        // 关键：chunk 边界 ≠ 事件边界，必须自己缓冲拼装
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const parts = buffer.split("\n\n");   // 事件以空行分隔
    buffer = parts.pop() ?? "";           // 最后一段可能不完整，留在缓冲区
    for (const part of parts) {
      const line = part.replace(/^data: /, "");
      if (line === "[DONE]") return;
      onDelta((JSON.parse(line) as { delta: string }).delta);
    }
  }
}

// 用法：
// const ac = new AbortController();
// stopButton.onclick = () => ac.abort();
// await streamChat(history, (d) => (output.textContent += d), ac.signal);
```

**buffer 那两行是流式解析的灵魂**：TCP 分块与 SSE 事件的边界不对齐，一个事件可能劈在两个 chunk 里——不做缓冲就会解析出残废 JSON。你背下这个模式，任何流式协议（SSE/自定义/分块 JSON）都是它的变体。`signal` 参数则是「停止」按钮的底层实现：`abort()` 断开连接，服务端的 `signal` 跟着中止。

> SSE vs WebSocket 速答（面试）：单向推送选 SSE（纯 HTTP、自动重连、代理/CDN 友好）；双向实时（语音、协作）才上 WS。LLM 对话 99% 是 SSE。

**服务端**（Route Handler，返回 AI SDK 的流式响应——协议里不只有文本 delta，还带工具调用、步骤状态等结构化 parts，useChat 自动解析）：

```ts
// app/api/chat/route.ts
import {
  APICallError, RetryError, consumeStream, createUIMessageStreamResponse, streamText, toUIMessageStream,
} from "ai";
import { model } from "@/lib/ai-sdk";
import { loadModelHistory, saveAssistantMessage, saveUserMessage, type ChatUIMessage } from "@/lib/store";
import { checkLimit, clientIp } from "@/lib/ratelimit";

export const maxDuration = 300;  // Vercel 函数时限：fluid compute 默认就是 300s，别调低成 60（第 19 章）

/** 把服务端异常映射成用户能看懂的话（v7 默认只给前端一句通用错误，不透传细节） */
function friendlyError(error: unknown): string {
  // 重试用完后抛的是 RetryError，真正的 HTTP 错误在 lastError 里
  const cause = RetryError.isInstance(error) ? error.lastError : error;
  if (APICallError.isInstance(cause)) {
    if (cause.statusCode === 429) return "请求太频繁，请稍后重试";
    if (cause.statusCode === 401) return "服务配置有误（API Key 无效），请联系管理员";
  }
  return "服务暂时不可用，请稍后重试";
}

export async function POST(req: Request) {
  if (!checkLimit(clientIp(req))) return new Response("Too Many Requests", { status: 429 });

  // 前端只发「本轮最后一条消息」（见 page.tsx 的 prepareSendMessagesRequest），历史以数据库为准
  const { conversationId, message } = (await req.json()) as { conversationId: string; message: ChatUIMessage };
  if (message.role === "user") {
    const text = message.parts.map((p) => (p.type === "text" ? p.text : "")).join("");
    await saveUserMessage(conversationId, message.id, text);
  }
  // store 的调用都写 await：SQLite 版是同步函数，await 一个普通值没有副作用；
  // 第 19 章换成 PostgreSQL 异步版时，这个路由一行不用改
  const history = await loadModelHistory(conversationId);   // 已包含刚存下的这条 user 消息

  let partial = "";                                   // 记下已生成的文字：被停止时要存成「未完成」
  const result = streamText({
    model,
    messages: history,
    instructions: process.env.SYSTEM_PROMPT ?? "你是一个简洁的中文助手。", // v7：system 已改名 instructions
    maxOutputTokens: 1024,
    // ★ 停止 = 真停止：用户点「停止」或关掉页面时 req.signal 被中止，
    //   它一路传到模型请求，上游连接被断开，服务端不再继续生成、不再继续计费
    abortSignal: req.signal,
    timeout: { firstChunkMs: 30_000, chunkMs: 15_000 },  // 30s 没出首个 token、或中途卡住 15s，就算超时
    onChunk: ({ chunk }) => { if (chunk.type === "text-delta") partial += chunk.text; },
    onEnd: async ({ text, usage }) => {               // v7：onFinish 已改名 onEnd；只有正常结束才会调用
      await saveAssistantMessage(conversationId, text, "done");
      console.log(`[usage] ${usage.inputTokens}+${usage.outputTokens}`);
    },
    onAbort: async () => {                            // 被中止（用户停止 / 超时）时调用，onEnd 不会调用
      await saveAssistantMessage(conversationId, partial, req.signal.aborted ? "cancelled" : "timeout");
      console.log(`[abort] ${req.signal.aborted ? "用户停止" : "超时"}，已生成 ${partial.length} 字，未标记为完成`);
    },
  });

  return createUIMessageStreamResponse({
    stream: toUIMessageStream({ stream: result.stream, onError: friendlyError }),
    consumeSseStream: consumeStream,   // 官方要求：保证被中止的流也能被正确消费、不泄漏连接
  });
}
```

逐段看设计：

- **前端只发最后一条**：历史以数据库为准，用户消息一收到就落库（带前端消息 id，`INSERT OR IGNORE`），所以「出错后重试」不会把同一个问题存两遍。
- **停止 = 真停止**：`abortSignal: req.signal` 是本章最重要的一行。没有它，用户点了「停止」，浏览器那头不动了，服务端却还在把整篇回答生成完——token 照样计费。官方文档的说法是：`stop()` 只中止客户端的 HTTP 请求，要让服务端的模型请求也停下，运行时必须把客户端断开传到 `req.signal`，**并且**你的路由要把它转给 `streamText`（2026-11 复核）。
- **半截回答绝不标成完成**：`onEnd` 只在正常结束时调用，存 `done`；被中止时调用的是 `onAbort`，存 `cancelled`（用户停止）或 `timeout`（超时）。`loadModelHistory` 只把 `done` 的消息喂回模型——半截回答不会污染下一轮上下文。
- **友好错误**：v7 默认只给前端一句通用错误，不透传服务端异常细节（这是安全修复）。想让用户看到「请求太频繁」，要在 `toUIMessageStream` 的 `onError` 里自己映射。注意例外：自 `ai` 7.0.171 起，**工具执行错误**默认把原文发给前端（2026-11 复核），本章没有工具不受影响；第 20 章带工具的路由要加 `redactToolErrors: true` 或 `onError`。
- **`consumeSseStream: consumeStream`**：官方要求，保证被中止的流也能被正确消费，不泄漏连接。

**客户端**（`@ai-sdk/react` 的 useChat）：

```tsx
// app/page.tsx
"use client";
import { useEffect, useState } from "react";
import { useChat } from "@ai-sdk/react";
import { DefaultChatTransport } from "ai";   // v5 起 api/body 收进 transport（不再是 useChat 顶层选项）
import type { ChatUIMessage } from "@/lib/store";
import { Markdown, StopButton, ErrorBar, Composer } from "./components";

/** 会话 id 放在 URL 的 ?c= 里：刷新页面还是同一个会话；没有就新建一个 */
export default function Page() {
  const [conversationId, setConversationId] = useState<string | null>(null);
  useEffect(() => {
    const url = new URL(window.location.href);
    let id = url.searchParams.get("c");
    if (!id) {
      id = crypto.randomUUID();
      url.searchParams.set("c", id);
      window.history.replaceState(null, "", url);
    }
    setConversationId(id);
  }, []);
  return conversationId ? <Chat key={conversationId} conversationId={conversationId} /> : null;
}

const textOf = (m: ChatUIMessage) => m.parts.map((p) => (p.type === "text" ? p.text : "")).join("");

function Chat({ conversationId }: { conversationId: string }) {
  // transport 只建一次（放 useState 初始化里），不要每次渲染都 new
  const [transport] = useState(() => new DefaultChatTransport<ChatUIMessage>({
    api: "/api/chat",
    // 只把本轮最后一条消息发给服务端，历史以服务端数据库为准（官方持久化推荐写法）
    prepareSendMessagesRequest: ({ messages }) => ({
      body: { conversationId, message: messages.at(-1) },
    }),
  }));
  const [stoppedIds, setStoppedIds] = useState<Set<string>>(new Set());
  const [conversations, setConversations] = useState<{ id: string; title: string }[]>([]);

  const { messages, setMessages, sendMessage, status, error, stop, regenerate } = useChat<ChatUIMessage>({
    id: conversationId,
    transport,
    throttle: 50,   // 每 50ms 最多刷新一次界面：官方内置的「批量 flush」，避免每个 token 都重渲染
    onFinish: ({ message, isAbort }) => {
      // 用户点了停止：这条回答是半截的，打上「已停止」标记，绝不当作完成
      if (isAbort) setStoppedIds((s) => new Set(s).add(message.id));
    },
  });

  // 刷新恢复：从服务端拿回这个会话的历史（含被停止的半截回答）和会话列表
  useEffect(() => {
    fetch(`/api/conversations/${conversationId}`)
      .then((r) => r.json() as Promise<{ messages: ChatUIMessage[]; conversations: { id: string; title: string }[] }>)
      .then((data) => { setMessages(data.messages); setConversations(data.conversations); })
      .catch(() => { /* 恢复失败不影响新对话 */ });
  }, [conversationId, setMessages]);

  const isUnfinished = (m: ChatUIMessage) =>
    stoppedIds.has(m.id) || m.metadata?.status === "cancelled" || m.metadata?.status === "timeout";
  const last = messages.at(-1);

  return (
    <div className="mx-auto flex max-w-4xl gap-4 p-4">
      <nav className="w-48 shrink-0">
        <a href="/">＋ 新会话</a>
        {conversations.map((c) => (
          <a key={c.id} href={`/?c=${c.id}`} className={c.id === conversationId ? "font-bold" : ""}>{c.title}</a>
        ))}
      </nav>
      <main className="flex-1">
        {messages.map((m) => (
          <div key={m.id} className={`chat ${m.role}`}>
            <Markdown content={textOf(m)} />
            {m.role === "assistant" && isUnfinished(m) && (
              <p className="text-amber-600">⏹ 已停止：这是未完成的回答，不会作为上下文发给模型</p>
            )}
          </div>
        ))}

        {/* 四个状态各有各的界面：submitted / streaming / ready / error */}
        {status === "submitted" && <p className="text-gray-500">思考中…</p>}
        {(status === "submitted" || status === "streaming") && <StopButton onClick={stop} />}
        {status === "error" && (
          <ErrorBar message={error?.message || "请求失败，请稍后重试"} onRetry={() => regenerate()} />
        )}
        {status === "ready" && last?.role === "assistant" && isUnfinished(last) && (
          <button type="button" onClick={() => regenerate()}>重新生成</button>
        )}
        <Composer disabled={status !== "ready"} onSend={(text) => sendMessage({ text })} />
      </main>
    </div>
  );
}
```

这里把 useChat 的 `status` 当成一个**显式状态机**来渲染，每个状态都有自己的界面：

| 状态 | 含义 | 界面 |
|---|---|---|
| `submitted` | 请求已发出，首个 token 还没到 | 「思考中…」+ 停止按钮（此时就允许停止） |
| `streaming` | 正在接收 | 打字机渲染 + 停止按钮 |
| `ready` | 空闲 | 输入框可用；如果上一条回答是半截的，额外给「重新生成」 |
| `error` | 请求失败 | `ErrorBar` 显示服务端映射好的友好文案 + 重试 |
| 「已停止」（不是 useChat 的状态） | 用户主动停止，或服务端超时 | 回答下方标「⏹ 已停止：未完成的回答」 |

「已停止」必须和「完成」区分开：`onFinish` 的 `isAbort` 告诉你这条回答是被停掉的；刷新后，服务端存的 `cancelled`/`timeout` 状态通过 `metadata` 带回来，界面照样标出。**用户看到的、数据库里存的、喂回模型的，三处对「这条回答没写完」的认知必须一致。**

上面用到的 4 个展示组件不在 AI SDK 里，给你一份最小实现（够用且可替换成你自己的设计系统）：

```tsx
// app/components.tsx —— 最小展示组件（样式自行 Tailwind 化）
"use client";
import { useState } from "react";
import ReactMarkdown from "react-markdown";

/** 模型输出是不可信内容：react-markdown 默认不渲染原始 HTML、会过滤 javascript: 链接，不需要 dangerouslySetInnerHTML */
export function Markdown({ content }: { content: string }) {
  return <div className="prose"><ReactMarkdown>{content}</ReactMarkdown></div>;
}
export function StopButton({ onClick }: { onClick: () => void }) {
  return <button type="button" onClick={onClick}>停止生成</button>;
}
export function ErrorBar({ message, onRetry }: { message: string; onRetry: () => void }) {
  return <div role="alert" className="error">{message} <button type="button" onClick={onRetry}>重试</button></div>;
}
export function Composer({ disabled, onSend }: { disabled: boolean; onSend: (text: string) => void }) {
  const [text, setText] = useState("");
  return (
    <form onSubmit={(e) => { e.preventDefault(); if (!text.trim() || disabled) return; onSend(text); setText(""); }}>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="输入消息…" />
      <button disabled={disabled || !text.trim()}>发送</button>
    </form>
  );
}
```

> 安全：模型输出属于不可信内容。不要把 `marked.parse()` 的结果塞进 `dangerouslySetInnerHTML`——模型（或被注入的网页内容）输出一段 `<img src=x onerror=…>` 就是 XSS（第 18 章 LLM05）。`react-markdown` 默认不渲染原始 HTML、会过滤 `javascript:` 这类危险链接，是更省心的选择。

## 5.5 会话持久化与恢复（SQLite，第 19 章换 PG）

```ts
// lib/store.ts —— 会话存储（教学用 SQLite；第 19 章迁 PostgreSQL）
import Database from "better-sqlite3";
import type { ModelMessage, UIMessage } from "ai";

const db = new Database("chat.db");
db.exec(`
CREATE TABLE IF NOT EXISTS conversations (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  created_at TEXT DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL,
  ui_id TEXT UNIQUE,                       -- 前端消息 id：重试时同一条 user 消息不会存两遍
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  content TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'done' CHECK (status IN ('done', 'cancelled', 'timeout')),
  created_at TEXT DEFAULT (datetime('now'))
);`);

export type MessageStatus = "done" | "cancelled" | "timeout";
/** 前端从 message.metadata 里读状态：被停止/超时的回答要显示成「未完成」 */
export type ChatMetadata = { status?: MessageStatus };
export type ChatUIMessage = UIMessage<ChatMetadata>;

type Row = { rowid: number; ui_id: string | null; role: "user" | "assistant"; content: string; status: MessageStatus };

/** 收到用户消息就先落库（INSERT OR IGNORE：重试/重新生成时不会重复） */
export function saveUserMessage(cid: string, uiId: string, text: string) {
  db.prepare("INSERT OR IGNORE INTO conversations (id, title) VALUES (?, ?)").run(cid, text.slice(0, 30));
  db.prepare("INSERT OR IGNORE INTO messages (conversation_id, ui_id, role, content) VALUES (?, ?, 'user', ?)")
    .run(cid, uiId, text);
}

/** 回答结束时落库：正常结束是 done；被用户停止是 cancelled；超时是 timeout——半截回答永远不标 done */
export function saveAssistantMessage(cid: string, text: string, status: MessageStatus) {
  db.prepare("INSERT INTO messages (conversation_id, role, content, status) VALUES (?, 'assistant', ?, ?)")
    .run(cid, text, status);
}

/** 给模型的历史：最近 40 条已完成的消息（未完成的半截回答不喂回模型） */
export function loadModelHistory(cid: string): ModelMessage[] {
  const rows = db.prepare(`
    SELECT role, content FROM (
      SELECT id, role, content FROM messages
      WHERE conversation_id = ? AND status = 'done' ORDER BY id DESC LIMIT 40
    ) ORDER BY id ASC
  `).all(cid) as Pick<Row, "role" | "content">[];
  return rows.map((r) => ({ role: r.role, content: r.content }));
}

/** 给页面的历史：全部消息（含未完成的），转成 useChat 认识的 UIMessage */
export function loadUIMessages(cid: string): ChatUIMessage[] {
  const rows = db.prepare(
    "SELECT id AS rowid, ui_id, role, content, status FROM messages WHERE conversation_id = ? ORDER BY id ASC",
  ).all(cid) as Row[];
  return rows.map((r) => ({
    id: r.ui_id ?? `db-${r.rowid}`,
    role: r.role,
    parts: [{ type: "text", text: r.content }],
    metadata: { status: r.status },
  }));
}

export function listConversations() {
  return db.prepare("SELECT id, title FROM conversations ORDER BY created_at DESC LIMIT 50")
    .all() as { id: string; title: string }[];
}
```

> 教学版直接用 `better-sqlite3`，不引入 ORM；第 19 章迁 PostgreSQL 时再上 Drizzle。注意 v7 的 `streamText` 默认拒收 `messages` 里的 `role: "system"`，所以表里只存 user/assistant，system prompt 走 `instructions`。

刷新恢复和会话列表走一个 GET 路由（页面加载时调用，见 `page.tsx` 的 `useEffect`）：

```ts
// app/api/conversations/[id]/route.ts —— 刷新恢复 + 会话列表
import { listConversations, loadUIMessages } from "@/lib/store";

export async function GET(_req: Request, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return Response.json({ messages: await loadUIMessages(id), conversations: await listConversations() });
}
```

**注意这里埋着第 1 章的伏笔**：每次请求都把最近 40 条历史发给模型——历史越长越贵，这正是第 14 章「上下文管理」要解决的问题，现在先做「最近 20 轮截断」这个朴素版。

## 5.6 用量统计与成本展示

后端在 `onEnd` 回调里拿到 `usage`（v7 的 `usage` 已是全部步骤的合计，直接用于计费），累计存表或内存；前端展示「本次对话已消耗 X tokens ≈ ¥Y」——按你 `.env` 里模型的单价算（价格见附录 B）。**这个小功能在面试里的作用超乎想象**：它证明你从第一天就有成本意识（第 17 章成本工程的前身）。被停止的回答也产生了费用（停止前生成的部分），想精确统计可以在 `onAbort` 里按已生成字数估算。

## 5.7 错误处理与限流：用户看到什么

| 后端情况 | 用户应看到 | 实现 |
|---|---|---|
| 429 限流 | 「请求太频繁，请稍后重试」+ 重试按钮 | AI SDK 自带重试（`streamText` 的 `maxRetries` 默认 2）；仍失败时由 `onError` 映射成这句话，前端 `status === "error"` 显示 |
| 流式中途断开 | 已收内容保留 + 重试 | useChat 的 error 状态 + `regenerate()` |
| 模型超时 | 回答标「已停止」+「重新生成」 | `timeout: { firstChunkMs, chunkMs }`；超时走 `onAbort`，存成 `timeout` |
| 用户点停止 | 回答标「已停止」，服务端同步停止 | `stop()` + `abortSignal: req.signal` |

**服务端限流**（防你的一张账单被脚本刷爆）：最小实现是每 IP 固定窗口计数器，已在 `route.ts` 第一行调用——生产换 Upstash Ratelimit（多实例共享计数）：

```ts
// lib/ratelimit.ts —— 单机内存版（教学用；多实例部署必须换 Redis）
const hits = new Map<string, { count: number; resetAt: number }>();

export function checkLimit(ip: string, limit = 20, windowMs = 60_000) {
  const now = Date.now();
  const rec = hits.get(ip);
  if (!rec || now > rec.resetAt) { hits.set(ip, { count: 1, resetAt: now + windowMs }); return true; }
  if (rec.count >= limit) return false;
  rec.count++;
  return true;
}

/** x-forwarded-for 可能是「客户端, 代理1, 代理2」的列表，取第一个；只信任部署平台注入的这个头 */
export function clientIp(req: Request) {
  return req.headers.get("x-forwarded-for")?.split(",")[0]?.trim() || "local";
}
```

**验证「停止真的停了」**（不花钱的做法）：把 `.env` 的 `BASE_URL` 指向一个本地假模型端点（几十行 Node 脚本，每 150ms 吐一个 token，并在连接被关闭时打印日志），点「停止」后看假端点是否立刻打印「连接已关闭」。这是第 0 章「先离线证明逻辑」在前端项目里的用法。

部署要点：`vercel deploy`（环境变量里配三件套）。两个坑：

1. **Vercel 上要显式开启请求取消**：官方文档说明，Vercel 的请求取消只支持 Node.js runtime，且要在 `vercel.json` 里给对应函数开 `supportsCancellation`；不开的话，`stop()` 只停了浏览器那头，服务端生成可能继续（2026-11 复核）：

   ```json
   {
     "functions": {
       "app/api/chat/route.ts": { "supportsCancellation": true }
     }
   }
   ```

2. **SQLite 在 serverless 上不持久**：要么本地跑通即可（教学版）、要么直接按第 19 章换 PG/云库。README 里写清这个限制反而是加分项（说明你知道边界）。

## ⚠️ 常见坑

1. **手动把路由改成 Edge runtime 又用了 better-sqlite3**——Next.js 的 Route Handler 默认就是 Node runtime（`edge` 已标记弃用）；只要别手动写 `runtime = "edge"`，better-sqlite3 就能用。显式写 `export const runtime = "nodejs"` 只是防御性声明。
2. **流式被缓冲**：过了 Nginx/代理后打字机变「一次性蹦出」——关代理缓冲（`X-Accel-Buffering: no` 响应头）。另外 Next.js 16.4.6 起 `next start` 自托管会自动压缩 Route Handler 响应；如果自托管后打字机变成一次性蹦出，先在流式响应头加 `"Cache-Control": "no-cache, no-transform"` 并实测（这一条的实际影响尚未核实）。
3. **「停止」只停了一半**：只调 `stop()`、服务端没把 `req.signal` 传给 `streamText`，模型照样生成完、照样计费；部署到 Vercel 还要开 `supportsCancellation`。另外官方说明 abort 与 useChat 的 `resume: true`（断线续传）不兼容，二选一。
4. **把半截回答当完整回答**：在 `toUIMessageStream` 的回调或客户端里不分青红皂白地「结束就存」，被停止的回答就以 `done` 混进历史，下一轮模型会接着一段残句往下聊。存的时候区分 `onEnd` 与 `onAbort`。
5. **AI SDK 版本混着旧资料写**：v5 之前的写法（`parameters`、`maxSteps`、`ai/react`）会直接编译报错；v6→v7 的改名（`system`→`instructions`、`onFinish`→`onEnd`、`stepCountIs`→`isStepCount`、`result.toUIMessageStreamResponse()`）仍能跑但已弃用、会告警。useChat 从 `@ai-sdk/react` 导入，`api`/`body` 自 v5 起收进 `DefaultChatTransport`。先查版本再看博客（v6→v7 迁移指南：https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0）。
6. **历史不截断**：聊 50 轮后每轮请求都全量重发——又贵又慢还可能超窗。先上「最近 N 轮」，第 14 章升级成摘要压缩。
7. **`onEnd`/`onAbort` 里抛错没人接**：流已返回客户端，持久化失败要自己捕获+记日志（第 16 章接告警）。
