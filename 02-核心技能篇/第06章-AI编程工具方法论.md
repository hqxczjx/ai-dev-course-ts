## 6.3 基本工作流：探索 → 计划 → 实现 → 验证

AI 编程的第一原则：**别让它一上来就写代码**。成熟的工作流是四段式：

```
① 探索（Explore）   让 AI 读代码/文档，回答「这个项目怎么组织、相关模块在哪」
                    ——产出：你对任务的理解 + 相关文件清单
② 计划（Plan）      让 AI 产出实现方案（改哪些文件、什么顺序、风险点）
                    ——产出：一份可审查的计划（SDD 的雏形，见 6.8）
③ 实现（Implement） 按计划分小步生成，每步可编译可运行
④ 验证（Verify）    测试 + Review + 对照计划逐条验收（6.6 的闭环）
```

为什么不跳过①②：AI 最大的错误来源不是「不会写」，而是**上下文不足下的自信脑补**（用了项目里不存在的 API、违反既有架构约定、重复造轮子）。探索与计划阶段就是给 AI 补上下文、给你补判断。

**任务粒度**：一次一个可验证的小任务（「加一个带重试的 fetch 封装」），不要「把整个项目重写一遍」。粒度越粗，验证越难，质量越失控。经验阈值：单个任务的产出 ≤ 300 行 diff，超出就拆。

## 6.4 项目级规则：CLAUDE.md（与 Cursor Rules）

CLAUDE.md 是放在项目根目录的「项目说明书」，AI 每次工作前自动读取。它解决的是**重复交代**问题——你不该在每次对话里重复「我们用 pnpm、别动 legacy 目录、错误处理走 Result 类型」。

一个生产可用的模板（按第 5 章项目 1 的真实结构定制，直接抄去用）：

```markdown
# CLAUDE.md

## 项目概述
流式 AI 对话应用（Next.js + TypeScript）。用户为中文使用者。

## 技术栈与约定
- 包管理器：pnpm 12（不要用 npm/yarn 命令；新依赖若报 ERR_PNPM_IGNORED_BUILDS，先问我再 approve-builds）
- 运行时：Node 24/26 LTS，ESM，TypeScript strict 模式
- 框架：Next.js App Router + Tailwind；服务端逻辑放 app/api/**/route.ts
- 数据库：SQLite（better-sqlite3，lib/store.ts）；教学版不用 ORM，第 19 章迁 PostgreSQL 时再引入 Drizzle
- LLM 调用：统一走 lib/ai-sdk.ts 导出的 model（AI SDK），禁止在组件中直接 import 模型 SDK
- 模型输出渲染：只用 app/components.tsx 的 Markdown 组件，禁止对模型输出用 dangerouslySetInnerHTML

## 常用命令
- pnpm dev：本地开发（端口 3000）
- pnpm typecheck（tsc --noEmit）与 pnpm lint：提交前必过

## 代码规范
- 错误处理：返回给前端的错误一律映射成友好文案，不透传服务端异常细节
- 命名：文件 kebab-case，组件 PascalCase，hooks 用 use 前缀
- 禁止：any（用 unknown + 收窄）、新增依赖前先询问、修改 lib/store.ts 的表结构前先说明迁移方案

## 注意事项
- 停止生成必须真正中止服务端请求（req.signal 传给 streamText），被停止的回答不能存成「已完成」
- 涉及付费 API 的改动要说明对 token 用量的影响
```

> 模板与项目 1 对齐（2026-11 复核）：项目 1 用的是根目录 `lib/`、`app/`（没有 `src/`），数据库是裸 `better-sqlite3`。写规则文件时，路径和技术栈必须和仓库**真实一致**——写错一个路径，AI 就会照着去找不存在的文件。

写好规则的四条心法：

1. **写「AI 常犯的错」而不是「人尽皆知的事」**。它知道 TypeScript 是什么，但不知道你们团队禁止 `any`。规则是从踩坑里长出来的：每次 AI 犯错且这个错会重复出现，就固化成一条规则。
2. **保持精简**。规则文件本身占上下文窗口——官方给的可操作锚点是 **CLAUDE.md 控制在 200 行以内**，且官方原话警告「臃肿的 CLAUDE.md 会让 AI 忽略你真正的指令」。跑 `/doctor prompt-audit`（Claude Code v2.1.283+）可让 Claude 找出过时或冲突的指令并给出修改建议；只对部分代码生效的规则移到 `.claude/rules/`（用 `paths` frontmatter 按路径加载），不占常驻上下文（2026-11 复核）。堆 500 行规则的代价是每次对话都变贵变慢，而且长文档中关键规则的遵循率反而下降。超过就删旧。
3. **命令给全**。构建/测试/lint 命令写清楚，AI 能自己跑验证，闭环质量天差地别。
4. **Cursor 等价物**：`.cursor/rules/` 目录（注意：**文件须为带 frontmatter 的 `.mdc`，纯 `.md` 放在该目录不生效**；旧版单文件 `.cursorrules` 在当前官方文档里已不再出现，别再新建；Cursor 也直接读取根目录和子目录的 AGENTS.md），语义相同——**理念可迁移，具体格式看各家文档**。

> 实践：给 Claude Code 用 `/init` 可自动生成初版 CLAUDE.md（已有文件时它给出改进建议，不会覆盖；设置环境变量 `CLAUDE_CODE_NEW_INIT=1` 会走交互式多阶段流程），然后按上面模板手工修剪——自动生成的版本通常太啰嗦。

**跨工具的规则文件：AGENTS.md**（2026-11 复核）：AGENTS.md 已成为多数编码 Agent 共用的项目说明文件（现为 Linux 基金会旗下 AAIF 的托管项目）。Cursor 与 Codex CLI 直接读取它；Claude Code 自 v2.1.277 起在项目**没有** CLAUDE.md 时读取 AGENTS.md，两者都有时只读 CLAUDE.md。想一份文件多工具共用，可以在 CLAUDE.md 里写一行 `@AGENTS.md` 导入。

**Claude Code 的扩展机制一张表**（官方把 CLAUDE.md、Skills、Subagents、Hooks、MCP、Plugins 并列为六种扩展方式，2026-11 复核）：

| 机制 | 何时加载 | 用来做什么 |
|---|---|---|
| CLAUDE.md / `.claude/rules/` | 每次会话常驻（rules 可按 `paths` 按需加载） | 项目约定 |
| Skills | 只常驻描述，用到才加载正文（6.7） | 可复用的方法与流程 |
| Subagents | 独立上下文 | 隔离调研、审查等大上下文任务，不污染主会话 |
| Hooks | 确定性执行，不依赖模型判断 | 必须强制的规则（如禁止改某目录）——要强制阻止某个动作用 PreToolUse hook，不能靠 CLAUDE.md |
| MCP | 工具协议（第 9 章） | 接入外部工具 |
| Plugins | 打包分发 | 把以上几种机制一起分发给团队 |

口诀：**建议写进 CLAUDE.md，强制交给 hook**。CLAUDE.md 里的规则模型「通常」会遵守，hook 是代码，一定会执行。

## 6.5 给对上下文：AI 编码质量的上游

第 14 章会系统讲「上下文工程」，这里是它在编码场景的速成版。**你给 AI 的上下文质量，直接决定它输出质量的上限**：

| 该给 | 常被漏掉 | 后果 |
|---|---|---|
| 相关文件全文（不只是文件名） | 只说「改一下登录逻辑」 | AI 脑补不存在的函数 |
| 接口/类型定义 | 让它「按现有风格写」 | 风格漂移、类型不匹配 |
| 明确的验收标准 | 「做一个差不多的」 | 返工 N 轮 |
| 错误的完整报错 + 复现步骤 | 截一段日志 | 瞎猜式修复 |
| 「不要做什么」 | 只说要什么 | 顺手重构了你不想动的东西 |

一个高效习惯：**为重复出现的任务建「上下文清单」**（放 CLAUDE.md 或 Skill 里）——「做 API 变更时必须提供：schema.ts、现有 route 文件、迁移规范文档」。把「想全上下文」从每次的脑力劳动变成查清单。

## 6.6 人机审查闭环：四道防线 + AI 代码缺陷模式库

这是本章的核心，也是面试必答（附录 A 第 10 题）。**审查 AI 代码不是逐行找 typo（那交给机器），而是抓住 AI 特有的失败模式**：

**AI 生成代码的五大典型缺陷**（建立你的「缺陷模式库」，Review 时按单扫描）：

1. **幻觉 API**：调用不存在的函数/参数（尤其库的新旧版本混淆——它按训练数据里的旧 API 写）。防线：typecheck + 看不熟的 API 查官方文档。
2. **边界条件缺失**：空数组、null、并发、超时的处理随手略过（它默认「正常情况」）。防线：单测覆盖边界 + Review 时专看输入校验。
3. **过度工程**：一个小需求给你抽象三层、加一堆「将来可能用到」的配置。防线：Review 时问「这段现在必要吗」，敢于让它删。
4. **安全盲区**：拼接 SQL、把 secret 打进日志、忘了鉴权——它对「看不见的威胁」不敏感。防线：安全清单（第 18 章）+ 高危区域人肉逐行。
5. **伪通过测试**：它写的测试迁就它的实现（先写实现再补测试，测试只是复述实现）。防线：核心逻辑的测试用例**自己**定（先测后码），AI 只帮实现。

**四道防线**（按成本从低到高排列，前者拦掉大部分，后者只处理漏网）：

```
第一道：typecheck + lint（每次保存/提交自动跑）——拦幻觉 API、低级错误
第二道：单测（AI 可写，用例你来审；核心路径用例你写）——拦边界缺陷
第三道：Code Review（人，聚焦缺陷模式库 + 与计划的偏差，不挑风格）
第四道：运行验证（真实环境跑通验收标准；高风险改动 = 支付/权限/删除 → 人肉逐行 + 预发冒烟）
```

**一条铁律贯穿全教程：看不懂的代码不合并**。让 AI 解释、查文档、或干脆重写——「能跑但没人懂」的代码是利息最高的技术债。这条铁律同时保护你的学习（第 0 章）和你的生产（本章）。「Vibe Coding」一词由 Andrej Karpathy 于 2025 年 2 月提出；Simon Willison 在讨论这个词时给出的判据与此一致：**如果你无法解释这行代码，就还没到能提交它的时候**（区分「vibe coding 玩具」与「vibe coding 生产」的分界线）。

## 6.7 Skills：把重复方法打包成可复用资产

当同一套工作流重复出现（「每次发布前要跑这三个检查」「每次加 API 要遵守这套步骤」），就值得写成 **Skill**——Claude 生态的可复用指令包，一个目录 + 一个 `SKILL.md`：

```markdown
---
name: release-checklist
description: 发布前检查清单。当用户要求发布/上线/deploy 本项目时使用。
---

# 发布前检查

1. 运行 pnpm typecheck && pnpm lint && pnpm test，全部通过才继续
2. 如果本次改了表结构，确认迁移脚本已写好并在本地跑过
3. 确认 .env.production 中 API Key 与预算上限已配置
4. 让我确认变更摘要（列出本次 diff 涉及的功能），确认后才执行部署命令
5. 部署后冒烟：访问 /api/health，跑一次最小对话请求验证流式输出正常
```

三个设计要点（与 Anthropic 官方最佳实践一致）：

1. **description 是触发器**：写清楚「什么时候用我」，AI 靠它决定是否加载——描述模糊的 Skill 永远不被触发。这是渐进式披露（progressive disclosure）的第一层：**启动时只常驻每个 Skill 的 name+description 元数据**，只看描述就能决定不加载，省上下文。
2. **正文按需加载（第二层）**：AI 判定相关后才读入完整 SKILL.md（官方建议 SKILL.md 正文控制在 500 行以内，详细资料拆到附属文件；`description` 与 `when_to_use` 合计超过 1,536 字符会在列表中被截断——2026-11 复核）；保持正文简短。**附属文件按需读取是第三层**：更长的参考资料放同目录附属文件，正文引用「详见 reference.md」——AI 需要时才读，量级不受限。这是渐进式披露的三层结构。
3. **Skill 是「方法」不是「知识」**：事实性知识放文档让它读；Skill 装「步骤+判断标准」这类流程性内容。

Skill 放在项目的 `.claude/skills/<name>/SKILL.md`（个人通用的放 `~/.claude/skills/`）；旧的自定义命令（`.claude/commands/`）已并入 Skills。Skills 遵循 Agent Skills 开放标准（agentskills.io，现为 AAIF 托管项目），Codex、Cursor 等工具同样能用（2026-11 复核）。官方仓库 github.com/anthropics/skills 有真实示例（文档处理、数据分析等），值得读两三个找手感。**市场信号**：SKILL.md 编写已进入 6+ 个 JD（硬之城、国投证券等），是你简历上实打实的加分项。

## 6.8 Vibe Coding vs Spec 驱动开发（SDD）：场合判断

两个词都进了 JD，考察的不是「会不会用」，是**场合判断力**（兆珑科技 JD 明说）：

| | Vibe Coding | Spec-Driven Development |
|---|---|---|
| 流程 | 描述意图 → AI 生成 → 跑起来看看 → 再调 | 写 spec.md（需求/接口/验收标准）→ AI 按规格生成 → 对照规格校验 |
| 适用 | 一次性原型、内部工具、探索验证、个人脚本 | 生产代码、多人协作、核心业务、任何「返工成本高」的模块 |
| 风险 | 隐性缺陷、无人理解的代码 | 前期慢；spec 本身写错则错到底（spec 也要 review） |
| 口诀 | 快糙猛，用完即弃 | 慢就是快，规格即契约 |

**SDD 的最小实践**（不依赖任何工具，今天就能用）：

```markdown
## spec.md —— 任务：会话导出功能
### 需求
用户可将会话导出为 Markdown 文件下载。

### 接口
POST /api/sessions/:id/export → 文件流（Content-Disposition: attachment）

### 验收标准
1. 导出内容含全部消息（按时间排序、标注角色）
2. 无权限访问他人会话时返回 403
3. 10MB 以上会话导出不超时（流式生成）
4. 单测覆盖 1-3 条

### 非目标
不做 PDF、不做批量导出（v2 再说）
```

写完 spec 先让 AI **审查 spec**（找漏洞：竞态、边界、安全），修完再让它实现——这一步「AI 审 AI」能拦截大量返工。生态工具（GitHub Spec Kit、OpenSpec 等）本质是把这套流程脚手架化，用法见附录 B；**先徒手掌握流程，再谈工具**。

## 6.9 沉淀：从个人习惯到「可讲述的方法论」

本章所有实践都要落到一个出口：`AI使用日志.md`（第 0 章建立的）每周整理一次，按此结构：

```
## 2026-10 第 2 周
- 交给 AI 的任务类型：样板代码 60% / 测试 25% / 重构 15%
- 典型失败 1：让 AI 加缓存，它脑补了 Redis 依赖（项目用的是内存缓存）
  → 修复：CLAUDE.md 增加一条「缓存一律用 src/lib/cache.ts」
- 典型失败 2：AI 写的分页测试只测了第一页
  → 修复：用例我写，实现它写
- 量化：本周 AI 生成约占 diff 的 65%；typecheck 拦截 3 次幻觉 API
```

三个月后这份日志就是：你面试第 10 题的答案、你的第一篇技术博客（10+ 岗位加分项）、你将来带团队的规范初稿。**「主动分享/沉淀」在软性要求里出现在 10+ 岗位**——这不是鸡汤，是简历上的一行。

## ⚠️ 常见坑

1. **把 Agent 当搜索引擎用**：一句「帮我修这个 bug」+ 一张截图。给足上下文（6.5），返工轮次从 5 降到 1。
2. **规则文件只写不删**：规则膨胀 → 遵循率下降 + 每次对话变贵。每月清理一次。
3. **用 AI 生成的代码绕过自己的理解**：短期快，长期断送学习与技术判断（多个 JD 明确考察「识破 AI 缺陷」的能力，这能力只能从 Review 中长出来）。
4. **对生产代码 Vibe Coding**：个人脚本随便 vibe；凡是上线、涉及钱和数据的东西，spec + 四道防线。
5. **一个会话干到底**：长会话里上下文被早期错误污染（AI 会顺着前面的错误继续走）。发现方向错了就开新会话，带着「教训摘要」重来。

## ✍️ 动手练习

**基础**：
1. 给你手上的任意项目（或本教程项目 1）写一份 CLAUDE.md，跑一周，记录 AI 被规则拦下的三次犯错。
2. 做 20 分钟「缺陷模式库」演练：让 AI 实现一个带边界条件的小功能（如「解析 CSV 并统计」），刻意只在它完成后检查 6.6 的五个模式，统计踩中几个。

**进阶**：
3. 写第一个 Skill（用 6.7 模板），主题选你真实重复的操作（如「给本项目加一个 API 路由的标准步骤」），实测触发是否准确。
4. SDD 全流程：为一个小功能写 spec.md（含验收标准与非目标）→ 让 AI 先审 spec → 实现 → 对照验收。记录这个流程与直接 vibe 的耗时/返工对比——这组数据就是你的面试答案。
