## 1.1 LLM 在做什么：一个超大规模的「接话机器」

把大模型想象成一个读过几乎整个互联网的接话机器：给它一段文字，它预测**下一个 token（词元）**是什么；预测出一个，接到原文后面，再预测下一个……循环直到它认为该停了。

```
输入：中国的首都是
模型内部： P("北")=0.87  P("上")=0.04  P("南")=0.02 ...
输出：北 → 拼回输入 → 预测下一个 → "京" → ...

最终输出：北京
```

三个立即成立的工程推论：

1. **模型没有「数据库」，只有「概率」**。它回答「首都」这类事实，是因为训练语料里这种接法出现得足够多，不是因为内部存了一张表。这直接解释幻觉（见 1.6）。
2. **输出是一点点长出来的**。你在前端看到的「打字机效果」不只是 UI 装饰——模型真的就是一个 token 一个 token 生成的。这就是**流式输出（Streaming）**存在的物理基础，也是第 5 章的主题。
3. **每次生成都有成本**。每个输出 token 都要跑一遍巨大的神经网络，输出越长越贵、越慢。这解释了为什么「让模型少废话」是真实的成本优化（第 17 章）。

> 💡 **一个常见误区**：模型「知道」它说过什么吗？——知道，但仅限于**当前这次对话送进上下文窗口里的内容**。它没有跨对话的记忆。你在两次会话之间感觉它「记得你」，是因为应用把历史消息重新发给了它（第 5 章实现，第 14 章深化为记忆系统）。理解这一点，你就理解了 AI 应用的一半架构。

## 1.2 Transformer 与注意力：工程视角的极简版

现代 LLM 都基于 Transformer 架构。作为应用开发者，你不需要会推导它，但需要两个直觉：

**直觉一：注意力（Attention）= 算相关性权重。**
处理「它」这个字时，模型会计算句中所有其他 token 与「它」的相关度，然后按权重融合信息来理解「它」指代谁。这就是模型能处理长距离指代、上下文语义的原因。你在 JD 里看到的「KV Cache」（DeepSeek Agent Harness 岗要求理解）就是注意力的计算缓存——已处理过的上文不必重算，这是推理加速的关键，也是「对话历史越长，首 token 越慢但有缓存后变快」的底层原因。

**直觉二：参数量 = 模型的「脑容量」。**
前沿模型的参数量普遍在千亿级以上（闭源厂商大多不公布具体数字），参数越多，能记住的模式越复杂，但推理成本也越高。「大模型贵而聪明、小模型便宜而快」这一简单事实，是第 17 章**模型路由**（简单任务用便宜模型，难任务才上旗舰）的全部依据。

> 想看可视化讲解：Jay Alammar 的 [The Illustrated Transformer](https://jalammar.github.io/illustrated-transformer/)（配图最经典）和 3Blue1Brown 的神经网络系列（B 站有官方搬运）是公认最好的两份入门材料。看不懂的部分跳过，不影响本课程。

## 1.3 Token 与分词：AI 开发的「度量衡」

**Token 是模型处理文本的最小单位**，介于字符和词之间。分词器（tokenizer）把文本切成 token 序列：英文大约 1 token ≈ 0.75 个单词；中文通常 1 个汉字 ≈ 1-1.5 个 token（按 1.5 估算更安全；同样的意思，中文往往比英文多花 token）。

**为什么你必须对 token 有手感**——它同时是四个东西的计量单位：

| Token 是什么的单位 | 影响什么 |
|---|---|
| 计费单位 | 输入 + 输出都按 token 收钱（输出通常贵 3-5 倍） |
| 上下文窗口的占用单位 | 窗口装的是 token，不是字符 |
| 速度单位 | 生成速度 = tokens/秒（人眼阅读约 5-8 tokens/秒，模型通常 20-100+） |
| 限流单位 | API 的 RPM/TPM 限额按请求次数和 token 数计 |

**估算手感**（面试和日常设计都够用）：

- 英文：1 token ≈ 4 字符
- 中文：1 个汉字 ≈ 1-1.5 个 token（不同厂商分词器差异大，按 1.5 估算更安全）
- 代码：波动大，约 1 token ≈ 3-3.5 字符
- 按上面的估算法，本教程一个典型章节约 5 千-1 万 token，整本二十多章合计十几万 token——**是的，把整本教程塞给模型是可行的**（主流窗口约 1M，见 1.4），但每次都要花这个钱

**成本速算练习**（务必动手算一遍，建立手感）：

> 用某模型处理一次请求：输入 8K token、输出 1K token。定价：输入 ¥2/百万token，输出 ¥8/百万token。
> 输入成本 = 8,000 ÷ 1,000,000 × 2 = ¥0.016；输出成本 = 1,000 ÷ 1,000,000 × 8 = ¥0.008；合计 ¥0.024/次。
> 一个日活 1000、人均 20 次调用的应用，每天成本 = 1000 × 20 × 0.024 ≈ ¥480/天。
> **结论写在你心里**：AI 应用的单位经济模型（unit economics）从第一天就要算。第 17 章的整套成本工程，全部建立在这条算术上。

各家模型具体价格（2026-11 复核）见[附录 B](../附录/附录B-资源索引.md)——写代码时不用背，但「一次调用大约几分钱」的量级感必须有。

## 1.4 上下文窗口：你的「内存管理」问题

**上下文窗口（context window）是一次请求中模型能「看见」的全部 token 上限**，包括：系统提示 + 全部历史消息 + 本次用户输入 +（有些厂商单独计）模型要生成的输出。

2026 年主流模型窗口从 128K-200K 到约 1M（1,048,576）token 不等（2026-11 复核：Claude、GPT-6、Gemini 4、DeepSeek、GLM-5.3、Kimi K3、Qwen 的上限都在 1M 左右；GLM-4.7-Flash 是 200K），但「窗口大」不等于「可以随便塞」，因为三件事：

1. **成本随窗口线性增长**：历史越长，每次请求的输入费用越高。一个 50 轮对话如果不做管理，第 51 轮要为前 50 轮全部重复付费。
2. **「迷失在中间」（Lost in the Middle）**：模型对上下文开头和结尾的内容注意力最强，塞在中间的关键信息容易被忽略。工程上的推论：**系统提示和关键指令放开头或结尾，检索到的资料放中间**（RAG 章节的标准做法）。
3. **窗口≠记忆**：窗口是单次请求的物理限制；跨请求的「记忆」需要你自己在应用层构建（存数据库、按需检索再注入）——这是第 14 章上下文工程的核心命题。

**上下文预算表**——给你的应用做设计时，先画这张表（示例：一个客服 AI）：

| 组成 | 预算（token） |
|---|---|
| System Prompt（角色+规则+工具说明） | 1,500 |
| 检索注入的知识片段（RAG） | 4,000 |
| 历史对话（滚动窗口/摘要压缩后） | 3,000 |
| 用户当前输入 | 500 |
| 预留输出 | 2,000 |
| **合计** | **11,000 / 128,000** ✓ |

这张表会在第 14 章进化成完整的上下文工程方法（组装/压缩/淘汰策略），现在你只需要建立「窗口是预算，要主动管理」的意识。

> **KV Cache 补充**（JD 高频词，一次讲清）：模型生成每个新 token 时要「回看」全部上文，注意力计算结果（Key/Value 矩阵）对相同前缀是可复用的。厂商利用这点做 **Prompt Caching**：前缀相同的部分（如系统提示、长文档）缓存后，命中部分的输入价格降到原价的约 2%-10%（各家不同，2026-11 复核：DeepSeek 约 2%，Claude 2.5%-10%，OpenAI GPT-6 系 5%-10%；有的厂商对写入缓存另收费，细节见第 17 章），且首 token 延迟显著降低。工程推论：**把不变的内容放请求最前面、变化的内容放后面**，是白捡的优化（第 17 章实操）。

## 1.5 采样参数：你每天都会拧的旋钮

模型每个 token 输出的是概率分布，采样参数决定「怎么从分布里挑」：

| 参数 | 作用 | 实践建议 |
|---|---|---|
| `temperature` | 随机性。0 ≈ 永远挑概率最高的（近确定)；1 正常；>1 更放飞 | **结构化输出/工具调用/分类：0-0.3**（要稳定）；**创作/brainstorm：0.7-1.0**（要多样性） |
| `top_p` | 只在累计概率前 p 的候选里挑（nucleus 采样） | 与 temperature 二选一调节即可，别同时拉满 |
| `max_tokens` | 限制输出长度（直连 OpenAI 新模型时参数名是 `max_completion_tokens`，Vercel AI SDK 里叫 `maxOutputTokens`） | 永远设置。防 runaway（模型抽风无限输出）= 成本保险丝 |
| `stop` | 遇到指定字符串即停止 | 少用，但在「让模型输出到某标记为止」的场景很干净 |
| `seed` | 固定采样种子 | 部分厂商支持，用于评测时提升可复现性（第 15 章会讲：即使固定 seed，结果也只是「更接近可复现」） |

> 注意各家 API 对「近确定性」的实现不同：有的用 `temperature: 0`，有的推荐专用参数（如 top_p 仅取 1）。调参时查附录 B 对应文档。
> **新一代推理模型干脆不让你调**（2026-11 复核）：OpenAI GPT-6 系在推理强度不是 `none` 时要求去掉 `temperature`/`top_p`，Anthropic 新版 API（2026-10-21 版）只要请求里带 `temperature`/`top_p`/`top_k` 就返回 400。课程主线用的 DeepSeek 等兼容端点仍支持这些参数——所以第 2 章的封装只在你**显式传了** `temperature` 时才发送它。
> **温度不影响事实正确性**——低温让模型更「自信」，不等于更「正确」。错误的事实低温下照样错得更稳定。事实问题靠 RAG 与工具（1.6），不靠温度。

## 1.6 训练三阶段与应用工程师的边界

模型出厂前的训练分三步，理解它们你就能说清「模型擅长什么、为什么不擅长什么」：

```
① 预训练（Pre-training）   海量文本上做"下一个词预测" → 学会语言与世界知识（贵，只有大厂做）
② 监督微调（SFT）          用高质量"指令→回答"对训练 → 学会"听话"（对话/遵循指令的能力来源）
③ 对齐（RLHF / RLAIF）     人类偏好反馈训练 → 学会"讨人喜欢"（有帮助、无害、格式好）
```

**对你是关键结论的边界问题**：215 岗位调研显示，AI 应用开发岗几乎不需要你训练模型（「不是算法岗，不做模型训练」是多份 JD 原话；要求微调的岗位不到 15% 且多为加分项）。你的战场是**把训练好的模型能力工程化落地**：Prompt、上下文、工具、检索、评测、成本。因此本教程不教训练；第 21 章会用一节讲清微调（LoRA/SFT）的概念与「什么时候才真的需要它」，确保你面试能聊、且能说清为什么你的方案不用它。

## 1.7 幻觉：成因与工程解法预览

**幻觉（Hallucination）= 模型一本正经地编造事实。** 成因在 1.1 已经埋下：模型天生做的是「概率上最顺的接话」，不是「事实检索」。当被问到训练数据里没有/很少/过时的内容时，概率最高的接法可能是个编造但「像样」的答案。SFT/RLHF 还会加剧它——奖励「自信、流畅的回答」，惩罚不了「我不知道」。

**工程解法的路线图**（这正是本教程主线的另一条叙事线）：

| 解法 | 原理 | 对应章节 |
|---|---|---|
| RAG（检索增强生成） | 先查资料再回答，答案有出处 | 第 12-13 章 |
| 工具调用 | 让模型去问真系统（数据库/API/搜索）而不是凭记忆 | 第 7 章 |
| 结构化输出 + 校验 | 输出必须通过 schema，格式性幻觉直接拦截 | 第 4 章 |
| Prompt 约束 | 「仅根据以下资料回答，资料没有就说不知道」 | 第 3 章 |
| 评测集回归 | 幻觉案例进评测集，改版后自动回归检查 | 第 15 章 |
| 降低温度 | **治不了幻觉**（见 1.5），但能减少随机跑偏 | — |

记住这张表的位置——学完第 13 章回看，你会发现自己已经全部掌握。

## 1.8 模型分类学：你将打交道的六类模型

AI 开发不只是「聊天的那个模型」。本教程会用到六类，先混个脸熟：

| 类型 | 干什么 | 何时用 |
|---|---|---|
| 指令/对话模型（LLM） | 理解与生成自然语言，可带工具调用 | 主力，绝大多数场景 |
| 推理模型（Reasoning） | 回答前先生成较长的内部思考链 | 数学/代码/复杂规划；更贵更慢，别当默认 |
| Embedding 模型 | 文本 → 高维向量（语义坐标） | 语义检索、RAG、聚类（第 12 章） |
| Rerank 模型 | 给「查询-文档对」打相关分 | 检索结果精排（第 13 章） |
| 视觉模型（VLM） | 理解图像/视频 | 多模态输入（第 21 章） |
| 语音模型（ASR/TTS） | 语音↔文本 | 语音交互（第 21 章） |

「**Model + Harness = Agent**」这个 JD 里的行业公式现在可以完整理解了：模型只是能力核心，外面套上你工程化的缰绳（harness：上下文管理、工具、循环、评测），才成为可靠的系统。这门课教的全部内容，就是造这条缰绳。

## 1.9 能力边界速查：什么别指望模型，什么该交给模型

**模型的硬伤**（工程上必须绕开，而不是「调一调」）：

- **精确计算与计数**：算术、日期推算、字符串精确处理——不可靠（概率机器做不了确定性运算）。解法：工具调用（让代码算）。
- **实时与私有信息**：训练截止后的新闻、你公司的内部文档——模型不知道。解法：RAG/工具。
- **严格格式保证**：不约束时偶尔破坏 JSON 格式。解法：结构化输出 API（第 4 章）。
- **长任务规划的一致性**：跨几十步的自主执行会漂移、死循环。解法：Agent 循环控制 + 评测（第 8、15 章）。
- **保密**：系统提示里写的「规则」不是安全边界，可被注入攻击绕过。解法：第 18 章。

**模型的强项**（放心交给它）：

- 语言理解与转换：摘要、改写、翻译、分类、抽取
- 非结构化 → 结构化：从文本里抽字段、打标签（配 schema 后极强）
- 代码生成与解释（配 AI 编程工具形成闭环，第 6 章）
- 作为「调度大脑」：根据意图选择工具、组织多步流程（第 7-11 章）

一个实用的思维实验：接到需求先问「**这个子任务的正确答案是唯一的、可机器验证的吗？**」是 → 写普通代码；否 → 考虑模型。「确定性程序、工作流与 Agent 的适用边界」本身就是高频面试题（附录 A 第 6 题），这个思维实验就是你的答题起点。

## ⚠️ 常见坑

1. **把上下文窗口当数据库用**。「窗口 128K，我把整个知识库塞进去不就行了？」——成本爆炸 + 迷失在中间 + 无法扩展。窗口放「本次需要的」，知识库放数据库，这是 RAG 存在的理由。
2. **以为 temperature=0 输出就完全确定**。多数实现只是「近似确定」，不同批次仍可能有差异。需要稳定输出靠结构化输出 + 少样本示例，不靠温度。
3. **只算输出不算输入的钱**。输入 token 通常占大头（尤其长历史对话），计费要看两头。
4. **用「聪明」评价模型而不看任务匹配**。旗舰模型做分类是浪费钱，小模型做复杂规划是浪费生命。选型 = 任务难度 × 延迟要求 × 成本预算（第 17 章系统化）。
