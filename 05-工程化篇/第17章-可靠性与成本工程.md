## 17.1 可靠性的心智模型：故障是常态

Demo 假设一切正常；生产假设**一切都会坏**：模型 API 会 429/5xx/超时，网络会断，工具会卡死，进程会重启，用户会在第 53 步取消任务。可靠性工程就是回答：**坏了之后，系统行为是什么？**

```
不可靠系统：坏了 → 崩溃/静默失败/重复扣款
可靠系统：坏了 → 按预案降级 → 状态可恢复 → 有人（或日志）知道发生了什么
```

六件可靠件（本章逐个装上）：

| 件 | 防什么 | 一句话实现 |
|---|---|---|
| 超时控制 | 单次调用/工具卡死 | AbortController + Promise.race |
| 重试策略 | 瞬时故障（429/5xx） | 指数退避+抖动（第 2 章已写，本章升级） |
| 降级链 Fallback | 主模型/主链路不可用 | 逐级切换备用方案（跨厂商要每家一个 client） |
| 幂等 | 重试导致重复副作用 | 意图日志 + 幂等键：重试之前先查状态 |
| 断点恢复 | 长任务中途死亡 | 持久执行/检查点 |
| 兜底体验 | 全都失败时用户看到什么 | 明确错误+转人工，而非白屏 |

### 超时控制（第 8 章预告的兑现）

只用 `Promise.race` 有个隐患：超时后调用方不等了，**底层请求/工具其实还在跑**——继续计费、继续产生副作用。所以超时要和 `AbortController` 绑在一起：时间到了先 `abort()` 通知被调方停下，再让调用方失败。课程的 `withTimeout` 就在 `agent/loop.ts` 里（节选，完整代码：`code/src/agent/loop.ts`）：

```ts
// agent/loop.ts（节选）—— 给任意异步操作加超时；超时后通过 AbortController 通知它停止
export async function withTimeout<T>(run: (signal: AbortSignal) => Promise<T>, ms: number): Promise<T> {
  const ac = new AbortController();
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => {
      ac.abort();
      reject(new Error(`工具执行超时（>${ms}ms）`));
    }, ms);
  });
  try {
    return await Promise.race([run(ac.signal), timeout]);
  } finally {
    clearTimeout(timer);
  }
}
```

注意参数是**函数** `run(signal)` 而不是一个已经在跑的 Promise——只有这样才能把 `signal` 交给被调方。用法：

```ts
// 能接 signal 的操作（fetch、chat() 的 signal 选项）：超时即真正中断
const page = await withTimeout((signal) => fetch(url, { signal }).then((r) => r.text()), 15_000);

// runAgent 里执行工具时（code/src/agent/loop.ts）：
//   result = await withTimeout(() => tool.execute(valid), toolTimeoutMs);
// 第 07 章的 execute 只收参数、不收 signal，所以超时后循环不再等它，但工具本身停不停取决于它自己。
// 进阶：给 ToolDef.execute 加第二个参数 signal，在工具里把它传给 fetch/数据库驱动。
```

（模型调用本身用 `chat()` 的 `signal` 选项或 SDK 的 `timeout` 选项更干净——同一个 `AbortController` 还能顺带支持用户「停止生成」。超时的离线测试见 `code/test/agent-loop.test.ts` 里的「工具超时」一条。）

### 重试的升级：从「再试一次」到「策略」

第 2 章的手写重试是入门版，生产还要考虑：**哪些错误重试**（429/5xx yes，400/401 no——就是 `lib/ai.ts` 的 `isRetryable()`；网络断开、超时这类拿不到状态码的错误，读请求可以重试，写操作要先按下面的幂等流程查状态）、**重试有没有副作用**（见幂等）、**重试时打不打扰用户**（流式场景：静默重连）。Fastly 式口诀：**Retry only what is retryable, only what is safe, only what is worth it.**

### 降级链：模型 Fallback 的标准实现

先说一个容易踩的坑：`lib/ai.ts` 的 `chat()` 只有**一个**按 `BASE_URL` 建好的客户端。只换 `model` 参数，就只能在同一家厂商的模型之间降级——把 `"glm-4.7-flash"` 发给 DeepSeek 的端点，只会得到「模型不存在」。跨厂商降级要**每家一个 client**（各自的 key、各自的 baseURL）：

```bash
# .env：除三件套外，降级链用到的每家厂商各配一个 key
DEEPSEEK_API_KEY=sk-...
GLM_API_KEY=...
```

```ts
// lib/fallback.ts —— 跨厂商降级链：每家一个 client（一个 baseURL 只认自家的模型名）
import OpenAI from "openai";
import type { ChatOptions, ChatResult } from "./ai";

// 每家厂商一个客户端，懒加载（与 getClient() 同理：没配 key 的厂商不影响其他厂商）
const PROVIDERS = {
  deepseek: () => new OpenAI({ apiKey: process.env.DEEPSEEK_API_KEY, baseURL: "https://api.deepseek.com", maxRetries: 0 }),
  glm: () => new OpenAI({ apiKey: process.env.GLM_API_KEY, baseURL: "https://open.bigmodel.cn/api/paas/v4/", maxRetries: 0 }),
} satisfies Record<string, () => OpenAI>;
export type Provider = keyof typeof PROVIDERS;

const clients = new Map<Provider, OpenAI>();
function clientFor(p: Provider): OpenAI {
  let c = clients.get(p);
  if (!c) { c = PROVIDERS[p](); clients.set(p, c); }
  return c;
}

export const CHAIN: { provider: Provider; model: string; reason: string }[] = [
  { provider: "deepseek", model: process.env.MODEL_GOOD ?? "deepseek-v4-pro", reason: "主力" },
  { provider: "deepseek", model: process.env.MODEL ?? "deepseek-flash", reason: "同厂商降级：便宜快速" },
  { provider: "glm", model: "glm-4.7-flash", reason: "跨厂商兜底：DeepSeek 整体故障时它还活着" },
];

export async function chatWithFallback(
  opts: Omit<ChatOptions, "model" | "retries">,
): Promise<ChatResult & { provider: Provider; model: string }> {
  const errors: string[] = [];
  for (const { provider, model, reason } of CHAIN) {
    const start = Date.now();
    try {
      const res = await clientFor(provider).chat.completions.create(
        {
          model,
          messages: opts.messages,
          ...(opts.temperature !== undefined ? { temperature: opts.temperature } : {}),
          ...(opts.json ? { response_format: { type: "json_object" as const } } : {}),
          max_tokens: opts.maxTokens ?? 1024,
        },
        { signal: opts.signal, timeout: 30_000 },   // 每一级自带超时：别让主力卡住整条链
      );
      const choice = res.choices[0];
      return {
        provider, model,
        text: choice?.message.content ?? "",
        finishReason: choice?.finish_reason ?? "unknown",
        usage: { input: res.usage?.prompt_tokens ?? 0, output: res.usage?.completion_tokens ?? 0 },
        durationMs: Date.now() - start,
      };
    } catch (err) {
      if (opts.signal?.aborted) throw err;             // 用户主动取消：不降级，直接停
      errors.push(`${provider}/${model}: ${String(err)}`);
      console.warn(`[fallback] ${provider}/${model} 失败，切下一级（${reason}）`);
    }
  }
  throw new Error(`全部模型不可用：${errors.join(" | ")}`);
}
```

三个细节：每一级都带超时（主力卡住时别让整条链陪着等）；**用户主动取消不降级**；降级与重试是两回事——上一级报什么错都换下一级（401 说明这家的 key 配错了，下一家照样能用），而同一级内部要不要先重试，取决于你的延迟预算。

降级不只是换模型：**功能降级**同样重要——RAG 检索失败 → 回答「知识库暂不可用」而不是报错；推荐模型失败 → 返回规则推荐的兜底结果。「每个外部依赖都想一句：它挂了我的 Plan B 是什么」——这个习惯就是 JD 说的「异常兜底机制设计」。

### 幂等：重试之前先查状态

```
不幂等：退款接口重试 3 次 = 退 3 次款
幂等化：执行前先记下「我要做什么」，重试之前先查「上次做到哪了」
```

LLM 应用里最需要幂等的地方是**工具的写操作**（建工单/发邮件/下单/写文件）。最难的不是「重复调用」，而是**执行到一半进程崩了（或超时了）**：重启后你不知道那张工单到底建没建。两种直觉做法都会出事——盲目重试可能重复建单、重复扣款；当作没发生可能漏单。正确做法是一句话：**重试之前先查状态。**

1. **执行前**先落一条意图记录：`status = started`，带幂等键（同一任务 + 同一工具 + 同一参数 → 同一个键）
2. **执行成功**后改成 `succeeded` 并存结果；**确定没执行**的失败（如参数被下游拒绝）改成 `failed`
3. 同一个幂等键再来：`succeeded` → 直接返回上次结果（replay），不再产生副作用；还停在 `started` → **状态未知**，不许重试，先拿幂等键去业务系统核对

（节选，完整代码：`code/src/reliability/ledger.ts`，含内存版 `MemoryLedger` 与落盘版 `JsonFileLedger`）

```ts
// reliability/ledger.ts（节选）—— 写操作的意图日志 + 幂等执行 + 崩溃后核对
export type LedgerStatus = "started" | "succeeded" | "failed";

export interface LedgerEntry {
  key: string;
  tool: string;
  args: unknown;
  status: LedgerStatus;
  result?: unknown;
  error?: string;
  updatedAt: string;
}

export interface Ledger {
  get(key: string): LedgerEntry | undefined;
  put(entry: LedgerEntry): void;
  list(): LedgerEntry[];
}

/** 幂等键 = 业务意图的指纹：同一任务里「同一工具 + 同一参数」只应产生一次副作用 */
export function idempotencyKey(taskId: string, tool: string, args: unknown): string {
  return createHash("sha256").update(`${taskId}|${tool}|${stable(args)}`).digest("hex").slice(0, 32);
}

export type IdempotentOutcome =
  | { status: "executed"; result: unknown }
  | { status: "replayed"; result: unknown }      // 之前成功过：直接返回旧结果，不再产生副作用
  | { status: "needs_reconcile"; entry: LedgerEntry }; // 上次停在 started：副作用可能已发生，先核对

export async function runIdempotent(
  ledger: Ledger,
  input: { key: string; tool: string; args: unknown },
  exec: (key: string) => Promise<unknown>,   // 把 key 传给下游：下游系统也应按它去重
): Promise<IdempotentOutcome> {
  const prev = ledger.get(input.key);
  if (prev?.status === "succeeded") return { status: "replayed", result: prev.result };
  if (prev?.status === "started") return { status: "needs_reconcile", entry: prev };

  const now = () => new Date().toISOString();
  ledger.put({ ...input, status: "started", updatedAt: now() });       // ① 先记意图
  try {
    const result = await exec(input.key);                              // ② 再执行
    ledger.put({ ...input, status: "succeeded", result, updatedAt: now() }); // ③ 记结果
    return { status: "executed", result };
  } catch (err) {
    // 注意：只有「确定没执行」的错误才该记成 failed（比如参数被下游拒绝）。
    // 超时这类「不知道执行没执行」的错误，保留 started，让重启后的核对流程处理。
    if (!isAmbiguous(err)) {
      ledger.put({ ...input, status: "failed", error: String(err), updatedAt: now() });
    }
    throw err;
  }
}

/**
 * 重启后调用：找出所有停在 started 的写操作，去业务系统按幂等键查一遍。
 * 查到了 → 补记 succeeded；查不到 → 标记 failed，允许安全重试。
 */
export async function reconcile(
  ledger: Ledger,
  lookup: (key: string) => Promise<unknown | undefined>,
): Promise<{ confirmed: string[]; safeToRetry: string[] }> {
  // …遍历 status === "started" 的记录，按 lookup 结果补记 succeeded 或 failed（见完整代码）
}
```

接到工具上：幂等键里的 `taskId` 来自请求（前端生成、重试时沿用），不来自模型。

```ts
// tools/ticket.ts（节选）—— 写操作工具接入意图日志
function createTicketTool(taskId: string, ledger: Ledger) {
  return defineTool({
    name: "createTicket",
    description: "为当前用户的订单创建售后工单。reason：repair 维修 / return 退货 / other 其他。",
    parameters: z.object({ orderId: z.string(), reason: z.enum(["repair", "return", "other"]) }),
    execute: async (args) => {
      const key = idempotencyKey(taskId, "createTicket", args);
      const out = await runIdempotent(ledger, { key, tool: "createTicket", args }, (k) => ticketApi.create(k, args));
      if (out.status === "needs_reconcile") {
        return { error: "STATE_UNKNOWN", hint: "上次提交结果未知，已转人工核对，请勿重复提交" };
      }
      return out.result;   // executed 或 replayed：对模型来说都是「工单已建好」
    },
  });
}
```

两个设计要点：参数尽量用**枚举/规范化后的字段**算键（`reason` 用枚举而不是自由文本），否则模型两次措辞不同就算出两个键；`exec` 把键传给下游（`ticketApi.create(k, …)`），下游系统也按它去重——这是第 18 章「完全中介」在可靠性上的对应：别只靠自己这一层。

离线测试（`code/test/ledger.test.ts`）把「建好了工单、但在记 succeeded 之前进程崩了」确定地演了一遍：重启后的新进程读同一个账本文件，第二次调用拿到 `needs_reconcile` 而不是重新建单；`reconcile()` 按幂等键查到工单已存在，补记成功；全程只有一张工单。`cd code && pnpm test` 就能跑。

## 17.2 持久执行：Inngest（崩了也能续跑）

第 8 章手写 Agent 的状态在内存里——进程一死全丢。第 10 章 LangGraph 的 checkpointer 解决了图内恢复；**应用层的长任务**（批量处理、多 Agent 流水线、定时任务）用持久执行平台更省事。主线选 **Inngest**（TS 原生、免费层 5 万次执行/月但只保留 24 小时 trace 历史；源码可得，服务端为 SSPL 并逐步转为 Apache-2.0，SDK 为 Apache-2.0；可自托管——默认 SQLite 单节点，生产需外接 Postgres + Redis，官方不对自托管提供直接支持）（2026-11 复核，inngest 4.26.x）：

```bash
pnpm add inngest
```

```ts
// inngest/function.ts —— 把第 11 章的多 Agent 流水线包成持久函数
// 依赖：pnpm add inngest
import { Inngest } from "inngest";
import { z } from "zod";
import { runAgent } from "../agent/loop";
import { structured } from "../lib/extract";
import { Plan, WORKERS } from "../multi/orchestrator";
import { openAIModel } from "../lib/model";

export const inngest = new Inngest({ id: "ai-app" });
const Review = z.object({ pass: z.boolean(), reason: z.string() });

export const researchPipeline = inngest.createFunction(
  // v4 写法：配置与触发器合并进第一个参数（v3 的「配置、触发器、handler」三参已移除）
  { id: "research-pipeline", retries: 2, triggers: { event: "app/research.requested" } },
  async ({ event, step }) => {
    const topic = String(event.data.topic);

    // ① 规划：一个 step。完成即存档，之后任何一步崩溃重放时都不会再花这次的钱（记忆化）
    const plan = await step.run("plan", () =>
      structured(Plan, [
        { role: "system", content: "你是任务规划器。把调研需求拆成 2-6 个子任务，分给 researcher / analyst / writer（writer 至多 1 个）。" },
        { role: "user", content: topic },
      ]),
    );

    // ② 并行步骤：每个子任务是「独立的」step（各自记忆化、各自重试），全部完成才进下一步。
    //    step ID 用子任务自己的 id：稳定且唯一，重放时才能对上号（别用随机数或时间戳）
    const workers = plan.subtasks.filter((t) => t.worker !== "writer");
    const research = await Promise.all(
      workers.map((t) =>
        step.run(`research-${t.id}`, async () => {
          const w = WORKERS[t.worker];
          const r = await runAgent({
            goal: `${w.system}\n任务简报：${t.goal}`,
            tools: w.tools, model: openAIModel(w.model), maxSteps: 5,
          });
          // 返回值会被序列化存档：只放可 JSON 化的数据
          return { id: t.id, ok: r.status === "done", text: r.status === "done" ? r.answer : `（失败：${r.status}）` };
        }),
      ),
    );

    // ③ 成文
    const report = await step.run("write", async () => {
      const material = research.map((r) => `## 子任务 ${r.id}\n${r.text}`).join("\n\n");
      const r = await runAgent({
        goal: `${WORKERS.writer.system}\n素材：\n${material}\n\n请按「${plan.aggregation}」写成完整报告。`,
        tools: [], model: openAIModel(WORKERS.writer.model), maxSteps: 2,
      });
      return r.status === "done" ? r.answer : material;
    });

    // sleep：定时/延迟也能持久化（进程死了计时照样走）；必须传 (id, duration) 两个参数
    await step.sleep("wait-1h", "1h");
    const review = await step.run("quality-check", () =>
      structured(Review, [{ role: "user", content: `这份报告是否回答了「${topic}」？\n${report}` }]),
    );
    return { review, failed: research.filter((r) => !r.ok).map((r) => r.id) };
  },
);
```

（`Plan`、`WORKERS` 来自第 11 章，完整代码：`code/src/multi/orchestrator.ts`；`runAgent` 来自 `code/src/agent/loop.ts`；`structured` 来自 `code/src/lib/extract.ts`。本地调试：`npx inngest-cli@latest dev` 起开发服务器，再把 `inngest` 与 `researchPipeline` 挂到你的 HTTP 服务上——按 Inngest 文档的 serve 写法。）

**并行步骤的写法是重点**：上面每个子任务各是一个 `step.run`，再用 `Promise.all` 等它们全部完成。如果写成「一个 `step.run` 里面 `Promise.all` 三个子 Agent」，那就只有**一个**持久单元——任何一个子 Agent 失败，整个 step 连同已经成功的子 Agent 一起重跑，钱花两遍。step ID 要稳定唯一（用子任务自己的 `id`），重放时平台靠它对上号。

`step.run` 的三件套就是持久执行的全部卖点：**自动重试**（步骤级 retries）、**记忆化**（重放时已完成步骤直接跳过）、**断点恢复**（崩溃后续跑）。第 10 章 LangGraph checkpointer 的概念，这里变成平台保证。Trigger.dev（v4）是对位选项（免费层每月 $5 计算额度；面向长时 AI Agent 的持久任务，无超时、崩溃可续）——面试被问「还知道什么」时报出它即可。

> **免费层计量口径**：Inngest 的「5 万次执行/月」按 `execution` 计——一次函数运行算 1 次，函数里每个 step 再各算 1 次。上面这个流程若拆出 3 个调研子任务，跑一次 = 1（函数）+ 1（plan）+ 3（research-*）+ 1（write）+ 1（sleep）+ 1（quality-check）= 8 executions，估算额度时别只数函数调用次数。

## 17.3 成本工程四板斧

（第 1 章的成本算术 + 第 16 章的成本看板在这里落地为工程手段。价格事实（2026-11 复核）：DeepSeek flash 已改**分时计价**——空闲时段输入 ¥1/输出 ¥4、高峰时段翻倍，缓存命中输入 ¥0.02-0.04；旗舰模型贵约 18-90 倍（按输出价对比 DeepSeek flash 空闲输出 ¥4；对高峰价则减半）：Sonnet 5.5 / GPT-6.1 Sol 约 18x，Opus 5.5 约 36x，Fable 5.2 约 72x，GPT-6 Astra 约 90x；中档 GPT-6.1 Terra 约 9x。）

### 板斧一：模型路由（贵模型只干难活）

```ts
// lib/router.ts —— 按任务类型分流：返回「哪家 + 哪个模型」
import type { Provider } from "./fallback";

export type Route = { provider: Provider; model: string };

export function pickModel(task: { kind: "classify" | "chat" | "reasoning" | "final-draft" }): Route {
  switch (task.kind) {
    case "classify":    return { provider: "glm", model: "glm-4.7-flash" };       // 免费：分类杀鸡不用牛刀
    case "chat":        return { provider: "deepseek", model: "deepseek-flash" };  // 空闲 ¥1 入 / ¥4 出：日常对话主力
    case "reasoning":   return { provider: "deepseek", model: "deepseek-v4-pro" }; // 需要多步推理的子任务
    case "final-draft": return { provider: "deepseek", model: "deepseek-v4-pro" }; // 最终产出质量优先
  }
}
```

路由结果是「哪家 + 哪个模型」而不只是模型名——和降级链一样，跨厂商就要换 client（`lib/fallback.ts` 的 `PROVIDERS`）。

第 11 章 WORKERS 的三档模型就是路由的架构版；更进阶还有**动态路由**（先让便宜模型答+自评置信度，低了再升级重答）——但先上静态路由，它已能砍掉 50-80% 成本。

### 板斧二：Prompt 缓存（把不变的放前面）

各家缓存机制与价格（2026-11 复核）：DeepSeek 命中输入 **¥0.02-0.04/M**（空闲/高峰；未命中 ¥1-2），自动生效。OpenAI 默认自动缓存（≥1,024 tokens 前缀完全一致才命中），缓存读为输入价的 **5%-10%**（GPT-6.1 Sol / Terra 5%，GPT-6 Astra / Luna 10%），GPT-6 系**缓存写入另计费**（30 分钟 1.25x、12 小时 2.5x），GPT-5.6 起可用 `prompt_cache_options` 设 TTL 或改为显式断点。**Claude 不会自动缓存**——必须在请求顶层加 `cache_control: { type: "ephemeral" }`（自动断点）或在稳定块上打最多 4 个显式断点，缓存顺序固定为 tools → system → messages；读 **0.025x-0.1x**（Fable 5.2 / 5.1 为 0.025x；Opus 5.5 / Sonnet 5.5 为 0.05x；Haiku 5.5 及更早为 0.1x），写入 5 分钟 1.25x、1 小时 2x。工程要点：**稳定前缀（system/工具定义/长文档）放消息最前、变化内容放后**——前缀对齐度越高命中率越高。这是「只改代码不换模型」就能拿到的最大单项折扣。另：DeepSeek 的空闲时段（工作日 9-12/14-18 点以外）全线半价——**把离线批处理/评测任务安排到空闲时段跑**，是分时计价下的白捡优化。

### 板斧三：上下文压缩（第 14 章的方法在这里变现）

长对话每轮全量重发的成本是 O(n²) 级增长的；滚动窗口+摘要压缩能把它压回 O(n)。第 14 章实现，这里记账：**历史超过预算阈值 → 触发摘要 → 输入 token 立降 60-80%**（你的实测数字会不同——用第 16 章看板验证，这正是「用样本和指标证明改进」的又一案例）。

### 板斧四：批处理与并行

- **Batch API**：离线任务（批量打标/评测）走批接口，普遍五折（OpenAI/Anthropic/GLM 均有；Gemini、Qwen Max/Plus 也是五折；Kimi K3 系 Batch 为标准价的 60%）（2026-11 复核）
- **并行**：串行子任务改并行，**延迟**降为最慢一支（省的是时间不是钱，但用户感知价值大）
- **结果缓存**：高频同问（FAQ）做语义缓存（第 12 章向量检索的旁路应用），或用 Cloudflare AI Gateway 的响应缓存（各计划可用，额度以官网为准）

## 17.4 成本-质量-延迟三角：会算账也要会取舍

三个目标互相牵制，工程是「显式选择牺牲谁」：

```
        质量（更好的模型/更长的上下文）
        ╱                ╲
   成本 ──────────────── 延迟
   （路由/缓存/压缩）      （并行/流式/小模型）
```

面试标准答法（背结构，填你的数据）：「我的项目 X 里，分类任务用免费模型接受 2% 的准确率下降，换 100% 成本下降；最终成文用 v4-pro 保证质量但用流式掩盖延迟；历史对话压缩后单轮成本降了 __%——每个决策都有第 16 章看板的数据支撑。」

**给用户的可靠性最后一里**：全部技术手段都失败时，用户看到的应该是「出错了，[重试] / 已记录，我们会跟进」——而不是无限转圈。错误态 UI（第 5 章 5.7）+ 错误上报（第 16 章）+ 兜底话术，合起来才是完整的可靠性。

## ⚠️ 常见坑

1. **对不可重试的错误疯狂重试**：400 参数错重试 5 次还是 400。错误分类（第 2 章）是重试的前提。
2. **降级链全部配同一家厂商**：厂商整体故障时一起死。跨厂商（DeepSeek→GLM）才是真兜底——而且要每家一个 client，只换 `model` 名字发到同一个 baseURL 是「模型不存在」。
3. **step.run 里塞进外部副作用却不做幂等**：Inngest 记忆化的是 step 结果，**进程外**的副作用（发的邮件）在 step 完成前崩溃时会随重试再执行一次——写操作类 step 自己走 17.1 的意图日志 + 幂等键。
4. **一个 step 里 `Promise.all` 一堆子任务**：那只是一个持久单元，一个失败全部重跑。并行要拆成多个 `step.run`，ID 稳定唯一。
5. **以为接了 Inngest 就不用 LangGraph checkpointer**（或反之）：应用层长任务用持久执行平台，图内细粒度恢复用 checkpointer，两者层次不同可并用。
6. **成本优化不看看板就动手**：不看第 16 章数据的「优化」是猜。先看哪类请求烧钱，再选板斧。
7. **缓存前缀里混进变化内容**（时间戳/随机 id 放头部）——命中率归零还纳闷。前缀稳定性要当作代码规范检查。换到 Claude 时还有一层：不加 `cache_control` 根本不缓存，命中率恒为 0。
8. **超时只做 `Promise.race`**：调用方不等了，底层请求还在跑、还在计费。超时要配 `AbortController`，把 `signal` 一路传下去。
9. **超时/断连后直接重试写操作**：状态未知时重试 = 赌它上次没成功。先查意图日志，停在 `started` 就去业务系统核对。
