## 14.1 上下文工程：Prompt 工程的「系统化升级」

第 3 章的 Prompt 工程管的是**单段指令怎么写**；上下文工程管的是**整份请求的预算分配**——system、历史、检索资料、工具结果、记忆，每一项都在抢同一个上下文窗口（2026 年主流模型从 128K-200K 到约 1M token 不等），而窗口的每一格都在花钱、都在影响注意力。

```
一次请求的上下文 = ┌ system（角色/规则）        ← 稳定，缓存友好（第 17 章前缀缓存）
                  ├ 记忆注入（用户偏好/事实）     ← 本章新成员
                  ├ 检索资料（RAG 片段）          ← 第 13 章
                  ├ 对话历史（窗口化/摘要化）      ← 本章核心
                  ├ 工具定义与结果                ← 第 7 章
                  └ 当前输入 + 预留输出
```

三个设计问题贯穿本章（也是面试的三连问）：

1. **装什么**（相关性判断：与当前任务无关的坚决不进）
2. **怎么裁**（满了怎么办：淘汰策略与压缩）
3. **从哪补**（跨会话的信息：记忆系统）

## 14.2 历史管理三级进化

第 5 章项目 1 用了最朴素的「最近 20 轮截断」。现在把它做成三级可进化的模块（每级都有适用场景，不是越高级越好）：

```ts
// context/history.ts —— 历史管理三级
import { chat } from "../lib/ai";   // 第 02 章的 chat()

export type Msg = { role: "user" | "assistant"; content: string };   // 导出：14.3 的记忆库要用

// Lv1 全量：短会话（<10 轮）最准，别过度设计——直接用 msgs 即可

// Lv2 滚动窗口：保留最近 N 条 + 第一条（首轮常含任务目标，不能丢）
export function slidingWindow(msgs: Msg[], keep = 12): Msg[] {
  if (msgs.length <= keep) return msgs;
  // 用 slice 而不是 msgs[0]：开了 noUncheckedIndexedAccess 后 msgs[0] 的类型是 Msg | undefined
  return [...msgs.slice(0, 1), ...msgs.slice(-(keep - 1))];
}

// Lv3 摘要压缩：窗口外的历史 → 一段摘要顶在开头（既省 token 又保住长程信息）
export async function compressedHistory(msgs: Msg[], keep = 8): Promise<Msg[]> {
  if (msgs.length <= keep) return msgs;
  const head = msgs.slice(0, -keep);
  const tail = msgs.slice(-keep);

  const { text } = await chat({
    temperature: 0.1,
    maxTokens: 400,
    messages: [
      { role: "system", content: "把对话历史压缩为要点摘要：保留用户目标、已做决定、关键事实与未决问题；所有数字、订单号、金额、承诺时间原样保留。用条目式，不超过 300 字。" },
      { role: "user", content: head.map((m) => `${m.role === "user" ? "用户" : "助手"}: ${m.content}`).join("\n") },
    ],
  });

  return [
    { role: "user", content: `<此前对话摘要>\n${text}\n</此前对话摘要>` },
    ...tail,
  ];
}
```

**三个进阶细节**（拉开差距的地方）：

1. **压缩时机按预算不按轮数**：累计 token 超 `预算×70%` 才触发（第 1 章的预算表在这里生效），避免无谓压缩花钱。
2. **摘要也要防丢失**：连续压缩会「摘要的摘要」导致信息漂移——保留一份滚动的「累积摘要」（新摘要=旧摘要+新裁掉的部分），而不是每次从头摘要。
3. **压缩的代价**：摘要是有损的（具体数字、语气、承诺可能被抹平）。**对高价值会话（客服投诉、交易确认）宁可全量+提前提醒开新会话，也别让关键事实消失在摘要里**——这是工程判断，不是技术炫技。

## 14.3 长期记忆：手写「抽取 → 存储 → 检索 → 注入」

跨会话记住用户（「上次说我对花生过敏」），四步管道——**你会发现这就是第 13 章 RAG 换了个数据源**：

```bash
# 依赖：第 12 章已装过 @lancedb/lancedb、apache-arrow；第 04 章已有 zod
pnpm add @lancedb/lancedb apache-arrow zod
```

记忆库沿用第 12 章的 `openAIEmbedder()` 与 LanceDB 写法，但**单独建库、单独建表**：记忆是用户私有数据，知识库是公共数据，混在第 13 章的 `chunks` 表里既难隔离又难删除。表里比第 12 章的 `Chunk` 多三列——`user_id`（隔离）、`kind`（分层，14.4）、`created_at`（过期与冲突，14.4 的 Consolidation）。

```ts
// memory/store.ts —— 最小可用的长期记忆系统（独立的 LanceDB 库 + 按用户预过滤）
import * as lancedb from "@lancedb/lancedb";
import { z } from "zod";
import { openAIEmbedder } from "../lib/embed"; // 第 12 章的 embedding 封装
import { structured } from "../lib/extract";   // 第 04 章 4.4.1 的通用结构化函数
import type { Msg } from "../context/history"; // 14.2

const embed = openAIEmbedder();                // 读 EMBED_* 环境变量（第 12 章）

const Extracted = z.object({
  memories: z.array(z.object({
    content: z.string().describe("一条独立的事实或偏好，第三人称，如：用户对花生过敏"),
    kind: z.enum(["fact", "preference", "goal", "episodic"]),
  })).max(5),
});

// 一行 = 一条记忆。比第 12 章的 Chunk 多了 user_id / kind / created_at：隔离与治理都靠它们
type MemoryRow = {
  id: string;
  user_id: string;   // 列名用 snake_case：LanceDB 的 where 里大写列名要加反引号，容易踩坑
  kind: string;
  text: string;
  created_at: string;
  vector: number[];
};

/** where 子句里的字符串字面量：单引号转义，防止 userId 拼出 SQL 注入（第 18 章） */
const lit = (s: string) => `'${s.replace(/'/g, "''")}'`;

export class MemoryStore {
  private constructor(
    private readonly db: lancedb.Connection,
    private table: lancedb.Table | null,
  ) {}

  /** 打开记忆库。与第 13 章知识库分开存：记忆是用户私有数据，知识库是公共数据 */
  static async open(path = "./data/memory"): Promise<MemoryStore> {
    const db = await lancedb.connect(path);
    let table: lancedb.Table | null = null;
    try {
      table = await db.openTable("memories");     // 已有表就打开，绝不 overwrite
    } catch {
      table = null;                               // 首次运行还没有表：等第一批记忆写入时再建
    }
    return new MemoryStore(db, table);
  }

  // ① 抽取：会话结束（或每 N 轮）后台跑；返回写入了几条
  async extract(sessionMsgs: Msg[], userId: string): Promise<number> {
    const { memories } = await structured(Extracted, [
      { role: "system", content: "从对话中抽取值得长期记住的信息：用户事实、稳定偏好、进行中的目标、重要事件。没有则返回空数组。只抽用户本人的信息，不要把临时状态（如「今天下雨」）当事实。" },
      { role: "user", content: sessionMsgs.map((m) => `${m.role}: ${m.content}`).join("\n") },
    ], { temperature: 0 });
    if (memories.length === 0) return 0;

    // ② 存储：向量化入库，每行都带 user_id
    const vectors = await embed(memories.map((m) => m.content));
    const now = new Date().toISOString();
    const rows: MemoryRow[] = memories.map((m, i) => ({
      id: `${userId}-${Date.now()}-${i}`,
      user_id: userId,
      kind: m.kind,
      text: m.content,
      created_at: now,
      vector: vectors[i] ?? [],
    }));
    if (this.table) await this.table.add(rows);
    else this.table = await this.db.createTable("memories", rows); // 第一批真实数据决定表结构，不需要种子行
    return rows.length;
  }

  // ③ 检索：先按 user_id 过滤、再在这个用户的记忆里找最近邻
  //    （LanceDB 的 where 默认是「预过滤」：别的用户记忆再多，也挤不掉这个用户的）
  async recall(userId: string, query: string, topK = 4): Promise<string[]> {
    if (!this.table) return [];
    const [qv] = await embed([query]);
    if (!qv) return [];
    const rows = await this.table
      .vectorSearch(qv)
      .where(`user_id = ${lit(userId)}`)
      .select(["text", "_distance"])   // 显式带上 _distance：只 select 普通列时 LanceDB 0.41 会打弃用警告
      .limit(topK)
      .toArray();
    return rows.map((r) => String(r.text));
  }

  // 治理：用户可见、可删（「记忆面板」页面就调这两个方法）
  async list(userId: string): Promise<{ id: string; kind: string; text: string; created_at: string }[]> {
    if (!this.table) return [];
    const rows = await this.table.query().where(`user_id = ${lit(userId)}`)
      .select(["id", "kind", "text", "created_at"]).toArray();
    return rows.map((r) => ({ id: String(r.id), kind: String(r.kind), text: String(r.text), created_at: String(r.created_at) }));
  }

  async forget(userId: string, id: string): Promise<void> {
    // 删除条件里同时带 user_id：即使 id 被猜到，也删不掉别人的记忆
    await this.table?.delete(`id = ${lit(id)} AND user_id = ${lit(userId)}`);
  }
}
```

④ 注入：每次请求前，按当前问题捞相关记忆，和压缩后的历史一起拼进请求：

```ts
// memory/context.ts —— 装配：记忆注入 + 压缩历史 + 当前问题
import type OpenAI from "openai";
import { chat } from "../lib/ai";
import { compressedHistory, type Msg } from "../context/history";
import { MemoryStore } from "./store";

// SYSTEM_PROMPT 用你第 3 章写的那份；这里给一个最小版
export const SYSTEM_PROMPT = "你是一个有长期记忆的助手。记住用户的稳定偏好与事实，但不要臆测。";

// 记忆库单例：第一次用到时才打开（并发调用共享同一个 Promise，不会重复初始化）
let memoryReady: Promise<MemoryStore> | undefined;
export function getMemory(): Promise<MemoryStore> {
  memoryReady ??= MemoryStore.open("./data/memory");
  return memoryReady;
}

// 注入模板：记忆放在 system 尾部，用标签包裹，并声明「可能过时」
// 返回类型写明：不写的话 role 会被推断成 string，传给 chat() 时编译报错
export async function buildContext(
  userId: string,
  query: string,
  history: Msg[],
): Promise<OpenAI.Chat.Completions.ChatCompletionMessageParam[]> {
  const memory = await getMemory();
  const [memories, recent] = await Promise.all([
    memory.recall(userId, query),
    compressedHistory(history),                // 14.2 的摘要压缩
  ]);
  const memoryBlock = memories.length
    ? `\n\n<用户记忆>\n${memories.map((m) => `- ${m}`).join("\n")}\n</用户记忆>\n（记忆可能过时，与用户最新表述冲突时以用户为准）`
    : "";
  return [
    { role: "system", content: SYSTEM_PROMPT + memoryBlock },
    ...recent,
    { role: "user", content: query },
  ];
}

/** 一轮带记忆的对话 */
export async function answer(userId: string, query: string, history: Msg[]): Promise<string> {
  const { text } = await chat({ messages: await buildContext(userId, query, history) });
  return text;
}
```

四个设计决策（每个都是面试谈资）：

1. **抽取是后台任务**：不该阻塞用户对话（第 17 章的 Inngest 可以把它挂到后台跑）。
2. **检索而非全量注入**：用户可能有几百条记忆，全塞进窗口是灾难——**记忆注入 = 对记忆库做一次 RAG 检索**，这就是「记忆系统复用 RAG 件」的含义。
3. **按用户隔离**：`user_id` 列 + 预过滤（先过滤再找最近邻）。只靠「先取 topK×3 再在代码里按用户筛」是不够的——别的用户记忆一多，这个用户可能一条都捞不回来；删除也要带 `user_id` 条件（第 18 章 LLM08 向量库弱点）。
4. **过时声明**：记忆是「过去的事实」——那句括号（冲突时以用户为准）是真实产品里防「记忆绑架对话」的关键细节。

## 14.4 记忆分层模型（JD 原词对齐）

字节 Aime、和生创新等 JD 使用的分层词汇，现在你可以逐层对应到自己写过的代码：

| 层 | 是什么 | 你的实现 |
|---|---|---|
| **短期记忆** | 当前会话的上下文 | 滚动窗口/摘要压缩（14.2） |
| **长期记忆** | 跨会话持久化的用户信息 | MemoryStore（14.3） |
| **情景记忆 episodic** | 「过往发生过什么」（事件序列） | kind: "episodic" 的记忆条目（可带时间戳） |
| **语义记忆 semantic** | 提炼出的事实与知识 | kind: "fact"/"preference" |
| **工作记忆 working** | 本次任务推理中的草稿 | Agent 的中间状态（第 8 章轨迹/scratchpad） |

**记忆整理（Consolidation）**：和生创新 JD 的前沿词——定期后台任务：去重（向量相似 >0.95 的合并）、冲突消解（「在上海」vs「搬到杭州了」→ 按 `created_at` 保留新的并记录变更，旧的用 `forget()` 删掉）、归档旧情景记忆为语义记忆。你的实现：定时任务（第 17 章 Inngest）+ 一轮 `structured()` 结构化处理。这个词你能讲出实现，面试直接上一档。

## 14.5 MemGPT 思想与现成方案

**MemGPT**（arXiv:2310.08560，Letta 前身）的核心比喻：**把上下文窗口当作操作系统的虚拟内存**——窗口是「内存页」，外部存储是「磁盘」，模型自己当「操作系统」决定换页（什么调入上下文、什么换出存档）。本章的管道是**代码当调度器**的版本；MemGPT 是**让模型参与调度**的版本。读懂这个思想，JD 里「理解 MemGPT 的上下文管理」你就有了回答框架。

现成方案（不必自造轮子，但要懂原理再上车）（2026-11 复核）：**Mastra Memory**（`new Memory({ options: { lastMessages: 20 } })` 起步，需在 Mastra 实例或 Agent 上配置 storage（如 `@mastra/libsql`）；可选开启观察式记忆（`observationalMemory: true`：后台 Agent 把旧消息压缩成观察日志，开启后 `lastMessages` 不再生效）、工作记忆=结构化用户数据、语义回忆=向量检索——**概念与本章手写件一一对应**）；mem0/Zep/Letta 为独立记忆服务，**均提供官方 TypeScript SDK**（`mem0ai` 含 `mem0ai/oss` 自托管入口、`@getzep/zep-cloud`、`@letta-ai/letta-client`；注意 `mem0ai` 3.x 仍依赖 Zod 3，会与课程的 Zod 4 并存），面试报得出名字与定位即可。

## 14.6 什么不该进上下文（上下文卫生）

上下文工程的一半是「不装什么」：

1. **原始工具大结果**：工具返回 50KB JSON 时只注入「与当前步相关的字段」（第 7 章返回值设计的深水版）——大结果落盘，传引用。
2. **失败尝试的尸体**：Agent 走错的三步（错误的工具调用与结果）留在历史里会持续误导模型（它爱模仿上下文里的模式）——重试时考虑只保留「错误教训」一行而非全过程。
3. **无关注入的 RAG 片段**：检索质量差时五个不相关片段比不检索更糟（注意力被稀释 + 幻觉诱因）——设相似度阈值，低于就宁缺毋滥。
4. **敏感信息**：能不进上下文的数据就别进去（进了就有被泄露进输出的概率，第 18 章）——权限系统在注入**前**过滤，而不是指望模型过滤。

## ⚠️ 常见坑

1. **把「记忆」做成「聊天记录全存库」**：每次把全部历史向量化入库 ≠ 记忆系统——没有抽取（噪音淹没信号）、没有分层、没有治理。记忆是**提炼物**不是**流水账**。
2. **摘要压缩丢关键事实**：订单号、金额、承诺时间被「摘要」抹掉——摘要 prompt 里显式要求「保留所有数字与承诺」+ 高价值会话不压缩。
3. **记忆被注入了但模型不认**：注入位置太深（迷失在中间）或没打标签。记忆放 system 尾部、用标签包裹、声明其「可能过时」——三件套。
4. **跨用户记忆泄露**：检索时没按 userId 过滤，或者「先检索再在代码里过滤」——A 的偏好出现在 B 的对话里是事故级 bug。过滤必须进查询（预过滤），测试集里放一条「跨用户隔离」用例（第 15 章）。
5. **压缩循环烧钱**：每轮触发一次摘要 → 对话越多越贵。按预算阈值触发 + 摘要结果缓存（下次从上次摘要续）。
6. **什么都塞给长期记忆**：抽取 prompt 不加「稳定信息」限定，把「今天下雨」也记成事实——垃圾记忆会长期污染每次检索。
7. **记忆库没 `open()` 就用 / 和知识库共用一张表**：前者第一次检索就空指针；后者让「删除某用户全部记忆」变成在公共知识库里动刀。记忆单独建库，用 `MemoryStore.open()` 拿实例。
