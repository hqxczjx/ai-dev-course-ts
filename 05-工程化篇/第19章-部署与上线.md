## 19.1 AI 应用部署的特殊性

传统 Web 部署 + 三个 AI 特有约束：

1. **流式响应**：反向代理不能缓冲（第 5 章 `X-Accel-Buffering: no`）；函数执行时限要拉长（一次 Agent 任务可能几分钟）
2. **长任务**：多 Agent 流水线不该住在请求周期里（HTTP 会断）——后台任务队列（Inngest）+ 前端轮询/订阅状态
3. **Secrets 与成本**：多家 API Key 的管理；以及「部署即烧钱」——预算熔断（第 17 章）要在上线前配好

## 19.2 路线一：Vercel（项目 1/2 的归宿）

Next.js 应用的最快路径：

```bash
pnpm dlx vercel
# 环境变量在 Dashboard 配：三件套 + EMBED_* + RERANK_* + LANGFUSE_*
```

三个必做：流式/Agent 路由显式写 `export const maxDuration = 300`（2026-11 复核：fluid compute 默认即 300 秒，Hobby 上限也是 300 秒；写明是为了防止项目级默认被改小，Pro 可到 800——**别写 60**，那会把流式路由的上限从 5 分钟降到 1 分钟）；**数据库不能用 SQLite 文件**（serverless 文件系统不持久）——项目 2 上 Vercel 时把 VectorStore 切到云（Upstash Vector 免费层，或 Neon PG+pgvector）；Langfuse 集成在 serverless 结束前 `forceFlush()`（第 16 章坑 2）。

## 19.3 路线二：VPS + Docker（项目 3 与生产主路线）

一台 2C4G 的 VPS（¥30-60/月）跑全部：应用 + PostgreSQL + Langfuse。

**先做一步配置**：在 `next.config.ts` 里开 `output: 'standalone'`——下面 Dockerfile 依赖的 `.next/standalone` 精简产物只有开了它才会生成，漏配则构建必败。

**Dockerfile**（Node 应用的标准三层缓存结构，runner 阶段参照 Next.js 官方 with-docker 示例）：

```dockerfile
# Dockerfile
FROM node:24-alpine AS deps
WORKDIR /app
# pnpm-workspace.yaml 必须一起拷：pnpm 12 的构建脚本放行记录（allowBuilds）写在里面，
# 少了它 pnpm install 会以 ERR_PNPM_IGNORED_BUILDS 失败
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable pnpm && pnpm install --frozen-lockfile

FROM node:24-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# 项目没有 public/ 目录时先建一个空的，下面 runner 阶段的 COPY 才不会失败
RUN mkdir -p public && corepack enable pnpm && pnpm build

FROM node:24-alpine
WORKDIR /app
# 容器内必须监听 0.0.0.0（Docker 会把 HOSTNAME 设成容器 ID，不覆盖就只监听那个地址）
ENV NODE_ENV=production PORT=3000 HOSTNAME=0.0.0.0
COPY --from=build --chown=node:node /app/.next/standalone ./
COPY --from=build --chown=node:node /app/.next/static ./.next/static
COPY --from=build --chown=node:node /app/public ./public
# 非 root 运行（官方示例同款）
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

> 三个小坑：① Dockerfile 的 `#` 只有写在**行首**才是注释，`ENV A=1  # 说明` 这种行尾注释会被当成参数，构建直接报错；② 镜像里用 `corepack enable pnpm`，它按 `package.json` 的 `packageManager` 字段装对应版本的 pnpm——和第 02 章本机用 `npx get-pnpm` 装的是同一个 pnpm，只是容器里不需要全局安装；所以 `packageManager` 字段和 `pnpm-workspace.yaml` 都要提交进 Git；③ 镜像用 `node:24-alpine` 与课程 Node 24 主线对齐（2026-11 复核：Node 24 为维护期 LTS，支持到 2028-04；想用 Node 26 LTS 就整体换成 `node:26-alpine`）。

**docker-compose.yml**（应用全家桶）：

```yaml
services:
  app:
    build: .
    ports: ["127.0.0.1:3000:3000"]                      # 只绑本机，由 Nginx/Caddy 反代对外
    environment:
      - DATABASE_URL=postgres://ai:${PG_PASSWORD}@db:5432/app   # 容器网络内互访
      - API_KEY=${API_KEY}                              # 真值来自宿主机 .env，不进镜像
      - BASE_URL=${BASE_URL}
      - LANGFUSE_BASE_URL=${LANGFUSE_BASE_URL}          # 指向另一套 Langfuse（见下）
      - LANGFUSE_PUBLIC_KEY=${LANGFUSE_PUBLIC_KEY}
      - LANGFUSE_SECRET_KEY=${LANGFUSE_SECRET_KEY}
    depends_on: [db]
    restart: unless-stopped
  db:
    image: pgvector/pgvector:pg17                        # PG 自带 pgvector 扩展
    environment: { POSTGRES_USER: ai, POSTGRES_PASSWORD: "${PG_PASSWORD}", POSTGRES_DB: app }
    ports: ["127.0.0.1:5432:5432"]                       # 只给本机跑迁移用，不对公网
    volumes: ["pgdata:/var/lib/postgresql/data"]
    restart: unless-stopped
volumes: { pgdata: {} }
```

**Langfuse 不放进这份 compose**：它本身就是一套多服务系统（web、worker、PostgreSQL、ClickHouse、Redis、MinIO），只写一个 `langfuse/langfuse` 镜像名会拉起一个缺依赖、缺密钥的残缺容器。按第 16 章 16.3 用**官方 compose** 单独起一套（`git clone https://github.com/langfuse/langfuse.git && cd langfuse`，改掉所有 `# CHANGEME` 的密钥后 `docker compose up -d`，文档：https://langfuse.com/self-hosting/deployment/docker-compose ），应用通过 `LANGFUSE_BASE_URL` 连过去。同一台 VPS 上跑两套 compose 时注意端口别冲突（两边都默认想用 3000），官方建议 VM 至少 4 核 16 GB 内存——2C4G 的小机器跑不动自部署 Langfuse，就用 Langfuse Cloud 免费层。

### 19.3.1 数据库：Drizzle + PostgreSQL（承接第 05、11、12 章）

第 05 章项目 1 用 SQLite 存会话，第 11 章的审批记录、第 12 章的 pgvector 都说「第 19 章配真实的 PG」——就是这里。用 Drizzle：表结构写成 TS，迁移文件由 `drizzle-kit` 生成、进 Git。

```bash
pnpm add drizzle-orm pg
pnpm add -D drizzle-kit @types/pg
```

```ts
// db/schema.ts —— PostgreSQL 表结构：项目 1 的会话消息 + 第 11 章的人工审批
import { index, jsonb, pgTable, serial, text, timestamp, uuid } from "drizzle-orm/pg-core";

// 与第 05 章 SQLite 版的三张表一一对应：conversations / messages（含 ui_id 去重与 status）
export const conversations = pgTable("conversations", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
});

export const messages = pgTable("messages", {
  id: serial("id").primaryKey(),
  conversationId: text("conversation_id").notNull(),
  uiId: text("ui_id").unique(),                       // 前端消息 id：重试时同一条 user 消息不会存两遍
  role: text("role", { enum: ["user", "assistant"] }).notNull(),
  content: text("content").notNull(),
  status: text("status", { enum: ["done", "cancelled", "timeout"] }).notNull().default("done"),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
}, (t) => [index("messages_conversation_idx").on(t.conversationId, t.id)]);

export const approvals = pgTable("approvals", {
  id: uuid("id").defaultRandom().primaryKey(),
  taskId: text("task_id").notNull(),
  toolName: text("tool_name").notNull(),
  args: jsonb("args").notNull(),                      // 当时请求执行的参数，审批人要看得到
  status: text("status", { enum: ["waiting", "approved", "rejected"] }).notNull().default("waiting"),
  note: text("note"),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
  decidedAt: timestamp("decided_at", { withTimezone: true }),
});
```

```ts
// db/index.ts —— 全应用共用一个 db 实例（第 11、12 章说的「你的持久层」就是它）

```

第 05 章 `lib/store.ts` 的 PG 版——导出的函数和类型同名同参数，只是变成了 async。第 05 章的路由调用时已经写了 `await`，所以路由代码一行不用改：

```ts
// lib/store.ts —— PG 版会话存储：替换第 05 章的 SQLite 版（同名同参数，改为 async）
import type { ModelMessage, UIMessage } from "ai";
import { and, asc, desc, eq } from "drizzle-orm";
import { db } from "../db";
import { conversations, messages } from "../db/schema";

export type MessageStatus = "done" | "cancelled" | "timeout";
export type ChatMetadata = { status?: MessageStatus };
export type ChatUIMessage = UIMessage<ChatMetadata>;

/** 收到用户消息就先落库（onConflictDoNothing：重试/重新生成时不会重复） */
export async function saveUserMessage(cid: string, uiId: string, text: string) {
  await db.insert(conversations).values({ id: cid, title: text.slice(0, 30) }).onConflictDoNothing();
  await db.insert(messages).values({ conversationId: cid, uiId, role: "user", content: text }).onConflictDoNothing();
}

/** 回答结束时落库：半截回答永远不标 done */
export async function saveAssistantMessage(cid: string, text: string, status: MessageStatus) {
  await db.insert(messages).values({ conversationId: cid, role: "assistant", content: text, status });
}

/** 给模型的历史：最近 40 条已完成的消息 */
export async function loadModelHistory(cid: string): Promise<ModelMessage[]> {
  const rows = await db
    .select({ role: messages.role, content: messages.content })
    .from(messages)
    .where(and(eq(messages.conversationId, cid), eq(messages.status, "done")))
    .orderBy(desc(messages.id))
    .limit(40);
  return rows.reverse().map((r) => ({ role: r.role, content: r.content }));
}

/** 给页面的历史：全部消息（含未完成的） */
export async function loadUIMessages(cid: string): Promise<ChatUIMessage[]> {
  const rows = await db.select().from(messages)
    .where(eq(messages.conversationId, cid)).orderBy(asc(messages.id));
  return rows.map((r) => ({
    id: r.uiId ?? `db-${r.id}`,
    role: r.role,
    parts: [{ type: "text" as const, text: r.content }],
    metadata: { status: r.status },
  }));
}

export async function listConversations() {
  return db.select({ id: conversations.id, title: conversations.title })
    .from(conversations).orderBy(desc(conversations.createdAt)).limit(50);
}
```

`package.json` 的脚本（CI 和部署都调这些名字）：

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "test": "tsx --test test/*.test.ts",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate"
  }
}
```

（`lint` 需要你配好 ESLint；还没配就先从脚本和 CI 里删掉这一步。`test` 与配套 `code/` 一致，用 Node 自带的 `node:test`；第 06 章写的 Vitest 也可以，换成 `vitest run` 即可。）

改了 `db/schema.ts` 就 `pnpm db:generate` 生成一份新的 SQL 迁移（在 `drizzle/` 目录，提交进 Git），部署时 `pnpm db:migrate` 应用所有未执行的迁移。

部署节奏：`git push` → VPS 上 `git pull` → `pnpm db:migrate`（在仓库目录跑，`DATABASE_URL` 指向 `127.0.0.1:5432`）→ `docker compose up -d --build`。迁移文件进 Git，**禁止手改线上库**——这是生产事故第一名；顺序固定为「先迁移、再起新版本」，新代码才不会读到旧表结构。

## 19.4 路线三：Cloudflare（Workers + AI Gateway）

边缘场景（全球低延迟、高并发轻请求）：`npx wrangler deploy`（Workers 对 HTTP 流式响应没有墙钟上限，但 Free 计划每个请求只有 10ms CPU 时间——等待模型返回不计 CPU，重计算别放这里）。AI 应用两个加分件：**AI Gateway**（一行 baseURL 改造，白嫖缓存/限流/成本分析，第 16-17 章用过）与 **Cloudflare Agents**（Durable Objects 有状态 Agent 运行时，第 10 章 demo 级了解的那个——长连接有状态 Agent 的部署归宿）。

**三条路线的选择**（面试「你怎么部署」的标准答案骨架）：

| | Vercel | VPS+Docker | Cloudflare |
|---|---|---|---|
| 适合 | Next.js 应用、快速上线 | 完整控制、Docker 生态、多服务 | 边缘/高并发/有状态 Agent |
| 成本 | 免费层起 | ¥30-60/月起 | 免费层起 |
| 心智 | 零运维 | 自己当运维 | 平台绑定 |

## 19.5 CI/CD：评测门禁进管道

把第 15 章的评测接进 GitHub Actions——**这是「AI 应用工程化」最体现专业度的一步**：

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
permissions:
  contents: read
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v6               # 读取 package.json 的 packageManager；v6 起声明支持 pnpm 12
      - uses: actions/setup-node@v7
        with: { node-version: 24, cache: pnpm }  # 与课程 Node 24 主线一致（promptfoo 需 ≥22.22）
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck && pnpm lint
      - run: pnpm test                           # 离线测试（第 08 章 FakeModel）：0 元，每次都跑
      - run: pnpm dlx promptfoo@latest eval      # 评测门禁：不达标即红
        env:
          DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}   # promptfoo 的 deepseek: provider 读这个
  redteam:                                       # 第 18 章的红队回归：花钱，只在 main 上跑
    needs: quality
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 24 }
      - run: npx promptfoo@latest redteam run    # 读仓库里的 redteam 配置（第 18 章 18.8 生成）
        env:
          DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}       # 攻击生成默认走 OpenAI；不用就在配置里换生成 provider
  deploy:
    needs: [quality, redteam]                    # 质量与安全全绿才部署
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      # Vercel：vercel deploy --prod --token=...（或 Vercel Git 集成自动部署）
      # VPS：ssh 到服务器 pull + db:migrate + compose up（secrets 存 SSH_KEY）
```

（Action 版本 2026-11 复核：GitHub 已于 2026-09-23 在 runner 上移除 Node 20，`checkout@v4`/`setup-node@v4` 这类 Node 20 时代的版本不再受支持；当前为 `actions/checkout@v7`、`actions/setup-node@v7`、`pnpm/action-setup@v6`。`pnpm/action-setup` 不负责装 Node，pnpm 版本取自 `packageManager` 字段，记得提交它。）

（promptfoo 也有现成的 `promptfoo/promptfoo-action@v1`，PR 上自动评论评测结果——第 15 章配过，需要 `permissions: pull-requests: write`。）

**顺手收紧 tsconfig**：CI 里的 `pnpm typecheck` 用的就是项目的 `tsconfig.json`。把它对齐配套 `code/tsconfig.json`——`strict`、`noUncheckedIndexedAccess`、`verbatimModuleSyntax` 都开着，`moduleResolution: "bundler"`。本地开发时嫌吵关掉过的检查，上线前在这里统一加回来，类型检查才真正是一道防线（第 06 章「四道防线」的第一道）。

## ⚠️ 常见坑

1. **.env 进了 Docker 镜像**——镜像层里翻得出来。构建用 `--build-arg` 也要小心；运行时注入（compose 的 `${VAR}`）才是正道。
2. **迁移与部署脱节**：新代码上线但没跑迁移（或反之）。把 `migrate` 放进部署脚本/容器启动入口，顺序固定。
3. **Vercel 函数超时上限**：当前 fluid compute 默认下 Hobby 上限 300 秒、Pro 800 秒（beta 可至 1800 秒）——超过 5 分钟的 Agent 长任务仍应改后台（Inngest/队列）+ 前端查状态，别硬扛请求周期。反过来也别把 `maxDuration` 写小：抄到旧教程的 `60`，流式回答一分钟就被掐断。
4. **docker-compose 的 CHANGEME 没改**（Langfuse 官方 compose 里的默认密钥）——公网暴露等于裸奔。改密钥 + 只绑内网端口（`127.0.0.1:3000:3000`）。
5. **CI 里跑了真付费调用且无上限**：评测门禁每次 push 都花钱。用便宜模型跑 CI 评测 + 缓存 + 只在 prompts 变更路径触发（第 15 章 workflow 的 paths 配置）。
6. **没有回滚方案就上线**：至少保留上一版本镜像/部署记录。AI 应用的问题常是「模型行为漂移」，回滚代码还不够——**固定模型版本**（别用 `latest`）也是回滚的一部分。
7. **镜像构建在本机过、在 CI/服务器挂**：最常见的三个原因——没拷 `pnpm-workspace.yaml`（构建脚本放行记录丢失，`ERR_PNPM_IGNORED_BUILDS`）、`COPY public` 但仓库里没有 `public/`、`packageManager` 字段没提交（corepack 不知道装哪版 pnpm）。
8. **容器能起、外面访问不到**：standalone 的 `server.js` 默认监听 `HOSTNAME`，而 Docker 把它设成了容器 ID。镜像里显式 `HOSTNAME=0.0.0.0`。

## ✍️ 动手练习

**基础**：
1. 项目 1 部署到 Vercel（含数据库云端化），配 CI（typecheck/test/deploy）。
