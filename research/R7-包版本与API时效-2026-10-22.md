# R7 · 包版本与 API 时效复核（2026-10-22）

> 复核对象：`/mnt/f/Download/AI开发教程-纯TypeScript`（纯 TypeScript AI 开发教程）
> 上次快照：2026-10-11（`research/核对-V7-版本与价格复查-2026-10-11.md`）
> 复核日期：2026-10-22
> 方法：先用 grep 定位教程中的具体代码与安装命令，再查官方 CHANGELOG / release notes / migration guide / npm registry；关键安装、导入与最小运行在本机实测（Node 24.13.1；pnpm 10.29.2 与 12.14.0；npm 11.9.0）。

## 一、结论摘要

### 1.1 必须改（P0）

1. **第 16 章 Langfuse 安装命令漏装两个直接依赖：`@langfuse/openai` 与 `@langfuse/tracing`。**
   这两个包不是 `@langfuse/otel` 的传递依赖。pnpm 的 isolated node_modules 下，读者只执行教程里的 `pnpm add @langfuse/otel @opentelemetry/sdk-node`，随后 `import { observeOpenAI } from "@langfuse/openai"` 和 `import { startActiveObservation } from "@langfuse/tracing"` 会直接 `ERR_MODULE_NOT_FOUND`。必须在安装命令中显式加入 `@langfuse/openai@6.0.1`、`@langfuse/tracing@6.0.1`。
   来源：<https://registry.npmjs.org/@langfuse/otel/6.0.1>（依赖列表不含这两个包）、<https://registry.npmjs.org/@langfuse/openai/6.0.1>、<https://registry.npmjs.org/@langfuse/tracing/6.0.1>。

2. **第 16 章 Langfuse 安装命令未锁 OpenTelemetry 2.x。**
   2026-10-20 OpenTelemetry JS 3.0.0 发布后，不锁版本的 `@opentelemetry/sdk-node` 会解析到 `0.300.0`。npm 11.9.0 实测直接 `ERESOLVE`：`sdk-node@0.300.0` 要求 `@opentelemetry/api >=1.10.0 <1.11.0`，而 Langfuse 6.0.1 的 OTel 2.x peer 线要求 api `<1.10.0`。pnpm 12.14.0 虽能完成安装，但 `pnpm peers check` 会报 `@opentelemetry/core@2.12.0` 需要 api `<1.10.0`（实际 1.10.0）、`@langfuse/otel@6.0.1` 需要 core `^2.0.1`（实际 3.0.0），属于官方未支持的混装。正确做法是把 `sdk-node@0.223.0`、`api@1.9.1`、`exporter-trace-otlp-http@0.223.0`、`otlp-exporter-base@0.223.0` 一并锁住（`0.223.0` 是 2.x 线最后一版）。
   来源：<https://github.com/open-telemetry/opentelemetry-js/releases/tag/v3.0.0>、<https://registry.npmjs.org/@opentelemetry/sdk-node/0.300.0>、<https://registry.npmjs.org/@opentelemetry/sdk-node/0.223.0>、<https://registry.npmjs.org/@langfuse/otel/6.0.1>。

3. **第 16 章安装命令在 pnpm 12 下会以非零码退出（`ERR_PNPM_IGNORED_BUILDS`）。**
   pnpm 11+ 的 `strictDepBuilds` 默认 `true`：依赖有未审批的构建脚本时安装以非零码结束。OTel 的传递依赖 `protobufjs` 会触发；第 12 章的 `pnpm add @lancedb/lancedb apache-arrow` 还会额外触发 `onnxruntime-node`、`sharp`。读者会看到 `pnpm add` 报错并停在半途。修复：安装后运行 `pnpm approve-builds protobufjs`（第 12 章再批准 `onnxruntime-node`、`sharp`），或在项目根 `pnpm-workspace.yaml` 写 `allowBuilds: { protobufjs: true }` 等，然后重新 `pnpm install`。
   来源：<https://pnpm.io/settings/build>（`strictDepBuilds` 默认 `true`，"the installation will exit with a non-zero exit code if any dependencies have unreviewed build scripts"）、<https://pnpm.io/cli/approve-builds>。

4. **第 9 章 MCP v2 的 Zod 说明错误。**
   教程写“zod 是 SDK 的 peer 依赖……Zod ≥3.25 下根导入同样可用”。实际 v2 的 `@modelcontextprotocol/server` / `client` **直接依赖** `zod ^4.2.0`，不是可选 peer；**Zod v3 已不支持**。官方迁移指南原话：“Zod v3 is no longer supported (v1 peer was ^3.25 || ^4.0).”“The v2 packages depend on zod ^4.2.0”。应改写为“装 `zod@^4.2.0`（课程用 4.6.7），Zod 4.0–4.1 会走兼容 fallback 并可能丢失 `.describe()`，建议 ≥4.2”。
   来源：<https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2>、<https://registry.npmjs.org/@modelcontextprotocol/server/latest>。

5. **第 2 章 TypeScript 7 的 `tsc --init --strict` 模板与教程代码不兼容。**
   TypeScript 7.0.2 生成的 tsconfig 含 `"types": []`、`noUncheckedIndexedAccess: true`、`exactOptionalPropertyTypes: true`、`verbatimModuleSyntax: true`。结果：第一个程序的 `process.env.API_KEY` 报 `TS2591`（找不到 `process`），`res.choices[0].message.content` 报 `TS2532`（对象可能为 undefined）。`tsx` 运行时不类型检查，所以 `pnpm exec tsx 01-basic.ts` 仍能跑；但 VSCode 全红、`tsc --noEmit` 失败。修复：用 `pnpm exec tsc --init --strict --types node`，并把上述三个 flag 改为 `false`，或直接用本报告 3.3 的最小 tsconfig。
   来源：<https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/>、<https://github.com/microsoft/typescript-go/blob/main/internal/execute/tsc/init.go>。

### 1.3 可不动（已核实无影响）

- **`ai` 7.0.137 → 7.0.148（patch）**：7.0.138–148 没有影响教程代码的破坏性变更。7.0.144 只把实验性低内存流式入口迁到 `experimental_streamTextLowMemory`，教程未用；`streamText`、`generateText`、`Output.object`、`tool({ inputSchema })`、`ToolLoopAgent`、`instructions`、`onEnd`、`convertToModelMessages`、`createUIMessageStreamResponse`、`toUIMessageStream`、`isStepCount`、`DefaultChatTransport` 全部仍在。第 5 章、第 10 章代码不需要改。
- **`@ai-sdk/openai` 4.0.91 → 4.0.99（patch）**：`openai("...")` 用法不变，仅 prompt cache 相关增量。
- **`@ai-sdk/react` → 4.0.152（patch）**：`useChat` + `DefaultChatTransport({ api, body })` 不变。
- **`@ai-sdk/mcp` → 2.0.81（patch）**：只在附录出现，无正文代码。
- **`openai` 7.32.0 → 7.42.0（minor，additive）**：`chat.completions.create` 与 `res.choices[0].message.content` 不变。
- **`zod` 4.6.5 → 4.6.7（patch）**：`zod/v4`、`z.toJSONSchema`、`.passthrough()` 等教程用法不变。
- **`@openai/agents` 0.20.0 → 0.21.0（minor）**：`new Agent({ name, instructions })`、`run(agent, "……")`、`tool({...})` 不变；0.21 移除 Runloop sandbox、收窄 usage detail，教程未用。
- **`@anthropic-ai/claude-agent-sdk` 0.3.296 → 0.3.308（patch）**：`query({ prompt, options })`、`permissionMode`、`canUseTool`、`allowedTools` 不变；0.3.302 只调整第三方 provider 在省略 `permissionMode` 时的默认行为，教程只有叙述、没有代码。
- **`@langchain/langgraph` 1.4.21 → 1.5.2（minor）**：教程用的 `StateGraph`、`StateSchema`、`MessagesValue`、`MemorySaver`、`interrupt`、`Command`、`graph.invoke(new Command({ resume: true }), config)` 不变。1.5.0 改的是 checkpoint saver 内部契约；`MemorySaver` 不受影响，只有 `PostgresSaver` 需要一次性 `setup()` 迁移（`task_path` 列），教程未用 PostgresSaver。
- **`langchain` 1.5.16 → 1.5.18（patch）**：教程没有直接调用其 API；1.5.13 的 `openai:` 字符串默认走 Responses 也不涉及。
- **`mastra` 1.33.0 → 1.35.0 / `@mastra/core` 1.75.0 → 1.79.0（minor）**：教程用的 `new Agent(...)` 与 `Memory({ options: { lastMessages: 20 } })` 仍有效；1.79.0 的 Agent controller session 破坏性变更教程未用。
- **MCP `@modelcontextprotocol/server` / `client` 2.3.1、`@modelcontextprotocol/hono` 2.0.2**：版本无变化，`McpServer.registerTool`、`StdioServerTransport`、`Client`、`StdioClientTransport`、`createMcpHonoApp`、`createMcpHandler` 与教程代码完全匹配；当前协议版本是 2026-07-28。
- **`@lancedb/lancedb` 0.40.0、`@qdrant/js-client-rest` 1.20.0、`drizzle-orm` 0.45.4、`next` 16.4.2、`inngest` 4.25.0、`promptfoo` 0.124.1、`autoevals` 0.4.1、`deepeval` 0.9.23、`e2b` 2.58.0 等**：无影响教程代码的破坏性变更（详见第二节）。
- **四个“已弃用/停更”判断全部仍成立**：`zod-to-json-schema` 已归档、LlamaIndex.TS 已归档、Chroma JS 只能连 server、`@modelcontextprotocol/sdk` 1.32.1 是 v1 维护线。详见 2.3。

### 1.4 无法核实清单

- **Langfuse 6.0.1 与真实 Langfuse 服务端（v4.59+）的端到端上报/UI 呈现**：本次只用本地 OTLP mock 验证了 `LangfuseSpanProcessor` + `startActiveObservation` 能发出 gzip span，没有连真实 Langfuse 实例验证 trace 树在 UI 中的呈现。
- **`LangfuseVercelAiSdkIntegration` 与真实 AI SDK 调用链路的 span 内容**：只验证了包可导入、`registerTelemetry(new LangfuseVercelAiSdkIntegration())` 可构造，没有跑完整 `streamText`/`generateText` 对话观察 span 细节。
- **`@anthropic-ai/sdk` 1.1.0 与 `@anthropic-ai/claude-agent-sdk` 0.3.308 的运行时组合**：教程没有直接代码；1.0.0（2026-10-21）带新 API version 的 major、1.1.0 为 additive，但二者一起跑的实际兼容性未实测。
- **pnpm 12 的 `ERR_PNPM_IGNORED_BUILDS` 是否在所有平台/配置下必现**：本机 pnpm 12.14.0 实测出现，官方文档确认 `strictDepBuilds` 默认 `true`；未穷举所有包和所有 pnpm 配置。
- **第 2 章之外各章的 TS7 类型检查**：只实测了第 2 章第一个程序；`types: []`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`verbatimModuleSyntax` 可能在其他章节还有零星类型报错，本次未逐文件跑 `tsc --noEmit`。运行时 `tsx` 不受影响。

### 1.5 一句话结论

**教程主体的 API 没有大面积失效，Langfuse v6 的写法也不需要替换。真正会让读者“照抄就报错”的是 5 个点：第 16 章漏装 `@langfuse/openai`/`@langfuse/tracing`、第 16 章 OTel 未锁 2.x、pnpm 12 的构建脚本审批、第 9 章 MCP v2 的 Zod 说明、第 2 章 TS7 的 `tsc --init` 模板。其余基本是版本号与叙述更新。**
