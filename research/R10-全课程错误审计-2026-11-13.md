## 1. 全局性问题（影响多章，先读这一节）

### G1 · P1 · 第 02 章的 tsconfig 让后续所有相对 import 编译失败

- 位置：`01-地基篇/第02章-环境搭建与第一个AI程序.md:124,130-140`
- 问题：`pnpm init`（pnpm 12）生成的 `package.json` 自带 `"type": "module"`（已实测：pnpm 12.18 生成 `"type": "module"`）；第 02 章推荐的 tsconfig 用 `"module": "NodeNext", "moduleResolution": "NodeNext"`。ESM + NodeNext 要求相对 import 写扩展名，而全课程写的都是 `import { chat } from "./lib/ai"`。`tsx` 运行时不受影响，但第 06 章「四道防线」第一道 `pnpm typecheck` 必然全红。
- 证据（A 轮，节选）：
  ```
  verbatim/hello/tool-loop.ts(6,23): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './lib/ai.js'?
  ```
  共 25 处，分布在第 05/07/08/09/10/11/12/13/14/15/17 章的 21 个文件；并把 12 个回调参数连带成隐式 `any`（TS7006/TS7031）。
- 修复（第 02 章 132-139 行替换为）：
  ```jsonc
  {
    "compilerOptions": {
      "target": "ES2023", "module": "Preserve", "moduleResolution": "Bundler",
      "strict": true, "types": ["node"], "skipLibCheck": true, "noEmit": true
    },
    "include": ["**/*.ts"]
  }
  ```
  并加一句：「本课程用 tsx 运行、tsc 只做类型检查，所以用 Bundler 解析，相对 import 不写扩展名」。（配套 `code/tsconfig.json` 已采用 `moduleResolution: "bundler"`。）

### G2 · P1 · openai 7.x 下 `tool_calls[i].function` / `ChatCompletionTool["function"]` 不再能直接访问

- 位置：第 07 章 135、177、180 行；第 08 章 136、140、146、159、168 行
- 问题：openai SDK 把工具调用类型改成联合 `ChatCompletionMessageFunctionToolCall | ChatCompletionMessageCustomToolCall`，`ChatCompletionTool` 也是 `FunctionTool | CustomTool` 联合。不先按 `type` 收窄就访问 `.function` 会编译失败。
- 证据：
  ```
  tool-loop.ts(35,40): error TS2339: Property 'function' does not exist on type 'ChatCompletionMessageToolCall'.
    Property 'function' does not exist on type 'ChatCompletionMessageCustomToolCall'.
  lib/ai.ts(92,82): error TS2339: Property 'function' does not exist on type 'ChatCompletionTool'.
  ```
- 修复：第 07 章 135 行改为 `as OpenAI.Chat.ChatCompletionFunctionTool["function"]["parameters"]`；所有遍历 `tool_calls` 的地方先写 `if (call.type !== "function") continue;`（配套 `code/src/agent/tool-loop.ts:48` 已这样写）。

### G3 · P0/P1 · 「在空目录 `pnpm add` 后 `npx tsx xxx.ts`」会落进 CommonJS，顶层 `await` 直接报错

- 位置：第 22 章 75 行（P0，见 22-1）；第 09 章 9.2 若读者另起 `order-server` 目录同理
- 证据：在 `pnpm add` 生成的（无 `"type"` 字段的）`package.json` 下运行含顶层 await 的文件：
  ```
  ERROR: Top-level await is currently not supported with the "cjs" output format
  ```
  对应 tsc：`TS1309 The current file is a CommonJS module and cannot use 'await' at the top level`、`TS1470 'import.meta' ... not allowed in files which will build into CommonJS output`。
- 修复：所有「新建目录」的命令统一写成 `pnpm init && pnpm add …`（pnpm 12 的 `pnpm init` 会写 `"type": "module"`），或在第 02 章明确「本课程所有项目 `package.json` 必须有 `"type": "module"`」。

### G4 · P2 · 正文仍未区分「完整可运行」与「片段/示意」，违反 NOTES.md 第 13 行约定

只有第 11 章 11.5（「接口示意」）、第 17 章 Inngest（「是示意」）、第 20 章 20.3（「自备组件」）做了标注。以下片段含未定义符号或非法语法却没有标注：第 04 章 4.6（`{ ... }` 函数体）、第 05 章 5.3 API 一览（`model/messages`）、第 07 章 7.5（`db`）、第 08 章 8.6 两段（`planWithLLM/reflectLLM/goal/task/tools`）、第 10 章 Mastra（`queryOrder`）、第 12 章 pgvector/Qdrant（`db/queryVec/sparseVec`）、第 13 章 13.3（`cleanText`）、第 16 章姿势三（`query/hybridSearch`）。
